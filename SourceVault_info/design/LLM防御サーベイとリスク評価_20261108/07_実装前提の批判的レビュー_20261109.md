## 3. 横断する指摘 (03・04 の両方に効く)

### I-01 [P0・設計懸念] 主体 (Principal) を決める仕組みを 1 つ定義する

**箇所**: 03 §6.1「Actor・Role は記録点のコードが決める」、§11.6 認可表、04 §15「主体の区分は 03 §11.6 と同じ」。

03 §11.6 は 5 つの主体ごとに可否を定めているが、関数が「自分は誰から呼ばれたか」を知る方法がどこにも書かれていない。現行コードにそれに当たるものは無い。webguard の DeclareContext (既定 HumanUser → Owner、`SourceVault_webingest.wl:380`、`SourceVault_webguard.wl:816`) と MCP の `_mcpClient` は自己申告で、02 が C1・C2 として問題にしたものである。主体が決まらなければ、認可表・Actor の記録・AuditView の制限・ReportMistake の Proposed 化はいずれも実装できない。

**修正案**: 03 §6.1 に「主体の束縛」の節を新設し、次を定める。

- 動的変数 `$SourceVaultPrincipal` を 1 つ置く。値は `<|"Kind" -> "OwnerFE" | "OwnerCode" | "Service" | "Model" | "MCP", "Channel" -> …, "Ticket" -> …|>`。未束縛 (Missing) のときは最も制限的な Model として扱う。
- 束縛する場所を列挙し、それ以外では束縛しない: (1) FE の ticket 発行関数 (I-02) が OwnerFE を Block で束縛、(2) `NBExecuteHeldExpr` (`NBAccess.wl:8545`) が OwnerCode、(3) `SourceVaultMCPCallTool` (`SourceVault_mcp.wl:4304`) が MCP (接続経路 = proxy のトークンから決め、`_mcpClient` は Claimed として記録だけ)、(4) `iExecSourceVaultToolCall` (`claudecode.wl:13037` 付近) が Model、(5) service の hook が Service。
- 既存の自己申告 (webguard の "Actor"、DeclareContext、MCP の authoredBy) はこの変数から導くように置き換える。これは 02 P0-12 の DeclareContext の件と同じ作業であり、1 つの変更にまとめる。
- 同一カーネルのコードが変数を書き換えられる限界は 03 表 1.1 の 4 行目にすでに書かれているので、そのまま参照する。

### I-02 [P0・設計懸念] ticket の実体を、既存の一回限り token から 1 つ選んで一般化する

**箇所**: 03 §5.4・§11.5・§12.8、04 §12.5 (SeriesApprovalTicket)、§15。

ticket の束縛規則 (主体・対象の digest・用途・nonce・期限、直前の再照合と原子的な消費) は十分に書かれている。しかし「どのモジュールが発行し、どこに消費記録を持ち、鍵をどこから取るか」が無い。既に 4 種類の署名つき一回限り token が別々に実装されている (2.2 節)。5 種類目を仕様に書くと、鍵・消費記録・失効がまた分かれる。

**修正案**:

- AutoTrigger の permit (`SourceVaultAutoTriggerMintPermit` / `VerifyPermit` / `ConsumePermit`) を基にする。理由: HMAC、nonce の消費記録ストア、SystemCredential の KeyRef、偽造・期限切れ・再利用・不一致の拒否試験 (AC-027) が揃っており、`SpecHash` の束縛を 04 §12.5 の `Bind` (digest の集合) に広げるだけでよい。
- 名前を `SourceVaultOwnerTicketMint` / `Verify` / `Consume` に一般化し、03 §11.5 と 04 §12.5 の両方がこれを指す。AutoTrigger の permit はその 1 用途 (Action = "Trigger") になる。
- MCP の AccessGrant は MCP の読取許可に限定して残す。capbroker の lease は LLM 境界用に残し、C-5 で統合する。Issue の keyed SHA256 は HMAC に揃える (小修正)。
- 発行関数は FE 専用の 1 つ (`SourceVaultOwnerTicketDialog[spec]`) に限り、ダイアログの表示内容の digest を Bind に含める。service カーネルには FE が無いので、発行は常に FE で行い、service 側は待ち行列 (04 §12.5 の AwaitingApproval の永続化) に入れて FE の tick が拾う。この「FE が拾う」経路を 04 §14.2 の状態遷移に明記する。
- 「ticket は FE の操作から来たと強く認証できない」という限界は 04 §17 にあるとおりで、変えない。

### I-03 [P0・確認] IdentityEvidence の既定で、実配備では L3 に到達できない

**箇所**: 03 §4.5 表 4.3、§7.1 ModelManifest、04 §12.2 G8、§1.4、§16.3 パイロット。

表 4.3 は Claimed (API が返すモデル名だけ) を「人が確かめる下書き (L1/L2)。命令採用・自動外部作用の入力には使わない」とし、G8 は「IdentityEvidence が段階の要求を満たす」ことを L3 以上の必須 Pass にしている。しかし実際の配備では LM Studio は別 PC (STRIXHALO128) で動き、FE 機からは重みを読めないので IdentityEvidence は常に Claimed になる (03 §16.1 がこの点を認めている)。クラウドモデルも Claimed 相当である。したがって、どのモデルを使っても L3 の条件を満たせず、04 §16.3 の研究費申請 (目標 L4)・成績集計 (L2〜L3) は仕様上到達不能になる。Attested に必要な別主体の署名鍵は v1.1 OP-3 で未導入である。

**修正案**:

- L3 (各外部作用を所有者が内容に束縛した ticket で確認する段階) では Claimed を許す。所有者が最終 payload を見て承認するので、モデルの同一性は安全性の条件ではない。表 4.3 の「許す利用」を L3 まで広げ、「L4 (自動実行) に Measured または Attested を要求」に改める。
- 「MeasuredByPeer」を追加する: LM Studio 機の service カーネルが自機で全体ハッシュを計算し、feeds に書く。同じユーザー・同じ同期アカウントなので独立した証人ではない (表 4.5 の注記を引く) が、「名前だけ」より強い。L3 の既定はこれで足りる。
- 04 G8 の文言を「PL ≥ 0.5 の処理に使うローカルモデルが利用でき、L4 なら Measured / Attested」に直す。

### I-04 [P0・確認] LLMCall の記録点では入力 Entity を決められない

**箇所**: 03 §6.1 DeclaredInputs、§6.2「claudecode LLMCall (全 provider、同期・非同期・tool loop): Inputs (Role 付き)」、§13.1 Inc2 の完了条件 Coverage ≥ 0.9、§7.1 Coverage。

LLMCall の記録点は 5 か所あり、どれも provider・モデル・トークン数しか持たない (2.2 節)。プロンプトは SourceVault の検索結果、ノートのセル、Directives、ツールの結果から組み立てられるが、組み立ての過程で EntityId は運ばれていない。「記録点のコードが Role を決める」には、claudecode の文脈組み立て (51,126 行のファイルの複数経路) に EntityId を通す配線が要り、Inc2 の規模を超える。記録点を足しただけでは Inputs が空の Activity ができ、§5.2 の規則で全出力が Unknown になる (安全側だが、Coverage ≥ 0.9 は満たせず Inc2 が終わらない)。

**修正案**: 入力の記録を「消費点 (LLMCall)」から「供給点 (SourceVault が内容を文脈へ渡した場所)」に移す。

- `SourceVaultSearch`・`SourceVaultKBAnswer`・MCP の get / search / get_document・NBAccess の読取 (評価スコープ透かし `SourceVaultEvaluationPrivacy` と同じ場所) が、返した Entity を `ServedToContext` Activity として emit する。Role は供給点の種類で決まる (検索結果 = Context、fs_read = Quote)。
- claudecode の 5 つの LLMCall emit を 1 つの helper にまとめ、`SessionKey` (provider|sessionKey、03 §4.1 の LineageSource = SessionKey) を 1 項目足す。
- service が SessionKey と時刻窓で ServedToContext と LLMCall を結合して LLMGenerate Activity を作る。結合できた入力の種類だけ Complete とし、残りは UnrecordedInputs に書く。
- これで Inc2 の記録点は claudecode 側 1 か所 + SourceVault 側 4〜5 か所になり、Coverage の分母も「供給点を通った派生」に定義し直せる。

### I-05 [P0・確認] 手編集を HumanEdit にする経路が無く、Instruction 系の日常編集が全部 Failing になる

### A-16 [P1・確認] 埋め込みの「ローカル provider」は LAN 先の LM Studio である

### A-19 [P2・確認] §2.2 の「L4 の候補」は v0.3 の規則では L4 にならない

研究費申請の実例は「外部作用は申請書の提出だけで、それ以外は内部処理 → L4 の候補」とあるが、保存先は `On Work/` (Dropbox 同期下) で、v0.3 の E2a に当たる。L4 に上げられるのは LocalState への下書きまでで、processed/ への移動は E2a (承認) になる。本文を訂正するか、「所有者専用の同期領域への移動は、系列の PL が同期の方策で許されるとき L4 に含める」という緩和を表 1.1 に明示的に書くかを決める。後者なら X-10 の期待値も変わる。

### A-20 [P2・確認] `WorkflowInputBlock` の実体
