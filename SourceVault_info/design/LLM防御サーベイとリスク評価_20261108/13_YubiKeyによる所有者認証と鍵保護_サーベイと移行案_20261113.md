# 13. YubiKey 5C による所有者認証と鍵保護: サーベイと移行案 (v0.1)

作成: 2026-11-13。位置づけ: 暗号化正典 v18 (`SourceVault_info/design/sourceVault_encryption_sharing_spec_v18.md` の 5 章・12〜14 章・19 章)、at-rest 方策 v0.2 (`sourcevault_notebook_atrest_encryption_spec_v0_2.md`)、文書 03 v0.4 (所有者 ticket と表 4.5)、文書 12 (受け入れて検証する安全設計) に対する追加の調査と設計案。

依頼 (所有者、2026-11-13): SourceVault の暗号化・認証の基盤を、SystemCredential だけに頼る形から、YubiKey 5C の FIDO2・TOTP・SSH 鍵などを前提とする認証を加えた形へ移せるか。所有者が関与すべき重要な認証では、YubiKey による多要素認証を使えるようにしたい。SystemCredential を残したハイブリッドも想定する。

本書は調査と設計案で、コードは変えていない。「確かめた」と書いたものは、コードを読んだか、本書を書いた機で読み取りの操作をしたもの。出典の無い一般的な知識には「(一般知識、未確認)」と付けた。

## 0. 要旨

1. **移行はできる。ただし「SystemCredential を YubiKey に置き換える」のではなく、鍵と操作を 3 段に分け、所有者の判断と根の鍵だけを YubiKey に移すハイブリッドにする。** service が無人で使う鍵 (台帳の MAC など) は SystemCredential に残す。YubiKey は触れることを求めるので、無人の処理には使えない (3 章)。
2. **いちばん効果が大きいのは所有者 ticket の署名を変えること。** 今の ticket は、SystemCredential に置いた共有の HMAC 鍵で作る。検証できる者は発行もできるし、発行を止めているのはカーネル内の関所で、暗号ではない。YubiKey の中の秘密鍵で署名し、検証は公開鍵だけで行う形にすると、同じ利用者の権限で動くコード (モデルが書いたコード、画面を操作するエージェント) は ticket を作れなくなる。公開鍵で検証するので、2 台の機と service が同じ YubiKey の ticket を検証できる (4.1 節)。
3. **次に効くのは、根の鍵と機密度の高いデータの鍵を YubiKey で包むこと (封筒暗号化)。** 鍵束の書き出し、鍵の交代、PL ≥ 0.95 の封印の解錠を、YubiKey + PIN が無いとできない操作にする。受取人は主・予備の YubiKey と紙の回復用 passphrase の 3 つにして、鍵の喪失 (at-rest 方策 v0.2 が「最大のリスク」とした点) に備える (4.3 節)。
4. **コードの外で、すぐに効くことがある。** Dropbox・GitHub・Microsoft・Google のアカウントに YubiKey を FIDO2 のセキュリティキーとして登録すると、文書 03 表 4.5 が「検知を保証しない」とした同期アカウントの乗っ取りの入口を塞げる (4.5 節)。
5. **TOTP は、所有者の確認にはほとんど効かない。** 検証する側が同じ種を持つので、その種を読めるコードは符号を作れる。使い道は、外部サービスの 2 要素と、数字しか打てない遠隔の経路に限られる (2.7 節)。
6. **手元の部品はそろっている (本書を書いた機で確かめた)。** YubiKey は USB 記述子から推定してファームウェア 5.7.4 (EUCLEAK の対象外)、有効な機能は FIDO2 とスマートカード (OTP は USB で無効)。Windows の WebAuthn API は版 9、Windows 付属の OpenSSH は 9.5p2 で FIDO 鍵に対応する。追加のソフトなしで、SSH 形式の FIDO 鍵による署名 (`ssh-keygen -Y sign`) を試せる。
7. **YubiKey でも守れないことがある。** YubiKey には画面が無いので、何に触れたかは PC の画面でしか確かめられない (表示のすり替え)。解錠中のメモリと、無人の処理の鍵 (H0) も守れない。触れる回数が多すぎると、承認が形骸化する (4.2 節・7 章)。

段取りは 5 章 (Y0〜Y6)、所有者に決めてほしいことは 6 章 (6.1 節に回答)。所有者との議論 (解錠の期間、みなし 1.0 の見直し、PL の 3 段と保管先の AccessLevel) は 8 章。

## 1. 今の仕組み (コードで確かめたこと)

### 1.1 鍵ストア

- `NBAccess_crypto.wl` が鍵を KeyRef で扱う。鍵の材料は SystemCredential (Windows では資格情報マネージャー) に 1 件ずつ置き (`NBAccess_crypto.wl:96-97`、名前は `SourceVault__k__…`)、材料を含まない索引は `~/.nbaccess/key-index.wxf.b64` に置く (同 :115)。資格情報 1 件の上限は 2560 バイトで、2026-07 に索引の書き込みが黙って失敗する事故があった (同 :104-112)。
- 暗号の操作は `NBEncryptWithKeyRef` / `NBMacWithKeyRef` などに閉じ、鍵の材料は NBAccess の外へ返さない (同 :11-16)。
- service のカーネルも 2026-11-11 から `$NBCredentialBackend = "SystemCredential"` で同じ鍵ストアを読む (台帳の MAC 鍵など 5 本)。

### 1.2 所有者 ticket

- `SourceVault_autotrigger.wl` の所有者 ticket は HMAC-SHA256 で署名する。鍵は `$SourceVaultOwnerTicketKeyRef` が指す SystemCredential の値 (`SourceVault_autotrigger.wl:850-853`)、署名する文字列は `iSVOTPayload` (同 :820)。
- 発行は `SourceVaultOwnerTicketDialog` の `ChoiceDialog` で所有者が「承認して ticket を発行」を押したときだけ (同 :1033-1060)。`SourceVaultOwnerTicketMint` は私的な変数 `$iSVOTDialogIssuing` を見て発行元を判定する (同 :976-984)。
- 検証も同じ鍵で HMAC を計算し直して比べる (同 :916-940)。**つまり、検証できる者は発行もできる。** 発行を止めているのは NBAccess の承認 head と私的な変数で、暗号ではない。
- 鍵は機ごとなので、ある機で発行した ticket は別の機では検証できない (同 :868-873 の注記)。

### 1.3 鍵束

`SourceVaultExportKeyBundle` は passphrase から scrypt (N = 131072) で包む鍵を作り、鍵の材料を包んで書き出す (`SourceVault_crypto.wl:517-554`)。passphrase が 12 文字未満なら止める。2026-11-11 に同期鍵を 2 台目の機へ運ぶのに使った。

### 1.4 既存の仕様が求めていること

- 暗号化正典 v18 §19.4: 根の署名鍵の指紋を OS の資格情報などに固定し、帯域外 (紙・別の端末) で確かめる。
- 同 §19.5: 「最終承認は、エージェントが直接作成・実行できる notebook cell や通常の ClaudeEval の action space の内側に置いてはならない。OS credential 書込み、別プロセスの確認ダイアログ、out-of-band fingerprint 入力、管理者署名など、エージェントが偽造しにくい経路で行う」。
- at-rest 方策 v0.2: 実装は可能、破損の危険は低い、**最大の危険は鍵の喪失**。
- 文書 03 v0.4 表 4.5: 「鍵に届く同一ユーザーコード・同期アカウント侵害は検知を保証しない」。

YubiKey は、§19.5 の「エージェントが偽造しにくい経路」と、表 4.5 の 2 つの穴に、直接答える部品である。

### 1.5 SystemCredential だけの場合に残る穴

| 攻撃者 | 今の SystemCredential だけの場合 | YubiKey を足すと |
|---|---|---|
| モデルが書いたコード (FE のカーネルで評価される) | NBAccess の関所で止める前提。関所に抜け道があれば、鍵を読む・ticket を作ることができる | ticket の署名鍵がカーネルに無いので、抜け道があっても ticket は作れない。触れることを求める要求は出せる (4.2 節) |
| 画面を操作するエージェント (computer use、RPA) | `ChoiceDialog` の「承認」を押せる | 押せても、YubiKey に触れることはできない |
| 同じ Windows の利用者で動く別のプロセス (Python のパッケージ、取り込んだツール) | 資格情報マネージャーの値は、同じ利用者のプロセスなら読める (一般知識、未確認)。NBAccess の関所は Wolfram のカーネルの中だけを見る | H1・H2 の鍵は取り出せない。H0 の鍵は同じく読める |
| 同期アカウントの乗っ取り (Dropbox など) | 鍵は同期領域の外だが、同期領域に置いたデータは読まれる。鍵束を同期領域に置くと passphrase の総当たり | アカウントの入口を FIDO2 で守れる (4.5 節) |
| PC の盗難 (RapterLake4t はノート) | ログオン状態で盗まれれば読める。オフラインの複製は Windows のログオンの強さと BitLocker 次第 (一般知識、未確認) | YubiKey を PC と一緒に持ち歩かなければ、H1・H2 は使えない |
| 所有者自身の誤操作 | 承認の窓で押し間違える | 触れる前に別の画面で確かめる手順を足せる (4.2 節) |

## 2. サーベイ: YubiKey 5C の機能と、Windows・Mathematica からの使い道

### 2.1 機能の一覧

| 機能 | 中身 | 鍵の在りか | 触れる・PIN | Windows で管理者なしに使えるか | Mathematica からの道 | SourceVault での用途 | 評価 |
|---|---|---|---|---|---|---|---|
| FIDO2 の署名 | 資格情報ごとの秘密鍵で署名 (Ed25519 / ES256) | YubiKey の中で、取り出せない | Windows の経路では毎回触れる。PIN は資格情報か要求で指定 | webauthn.dll 経由なら可。直接の HID は管理者が要る | 補助の exe、python-fido2、ssh-keygen | 所有者 ticket の署名 (H1・H2) | ◎ |
| FIDO2 の PRF (hmac-secret) | 資格情報ごとの秘密と salt から 32 バイトを導く | 同上 | 同上 | webauthn.dll の PRF として渡せる道がある (要実測) | 補助の exe、python-fido2 | 鍵を包む鍵 (KEK) | ○ (要実測) |
| SSH の sk 鍵 (`ed25519-sk`) | FIDO2 の資格情報を SSH の鍵として使う。手元のファイルは参照だけ | 同上 | 触れる。`-O verify-required` で PIN も | 付属 OpenSSH 8.9 以降 (手元は 9.5p2) | `ssh-keygen -Y sign` / `-Y verify` を `RunProcess` で | ticket の署名 (最短の道)、GitHub の署名と push、LAN の機への SSH | ◎ (Windows での `-Y sign` は要実測) |
| PIV (スマートカード) | RSA 2048〜4096・ECC・Ed25519・X25519 の鍵 (主 4 + 予備 20 のスロット) | YubiKey の中 | PIN の方針 (never / once / always) と触れる方針 (never / cached / always) を鍵ごとに、生成時に固定 | Windows のスマートカードの仕組みで可 | PowerShell + .NET (CNG)、age-plugin-yubikey、ykman | 鍵を包む (H2・PL ≥ 0.95)、基準 (baseline) への署名 | ◎ |

| OATH (TOTP / HOTP) | 種から 6〜8 桁の符号 | 種は YubiKey の中。ただし検証する側も同じ種を持つ | 資格情報ごとに触れるを要求できる | ykman、Yubico Authenticator | ykman | 外部サービスの 2 要素 (FIDO2 が無いとき)、遠隔の経路 | △ (2.7 節) |
| OTP (Yubico OTP、HMAC-SHA1 のチャレンジ応答) | 2 スロット | YubiKey の中 (書き込みは PC から) | 触れるは設定で | 手元の鍵は USB の OTP が無効。Windows で HID の排他に当たる報告あり | ykman | 鍵を包む (KeePassXC 方式) | △ |

### 2.2 ファームウェアの版

- **5.7** (2024): FIDO2 の発見可能な資格情報が 100 件に、PIV に RSA 3072 / 4096・Ed25519・X25519 と鍵の移動・削除、OATH は 64 件、RSA と ECC の演算は Yubico 自身の暗号ライブラリで行う ([5.7 の仕様](https://docs.yubico.com/hardware/yubikey/yk-tech-manual/yk5-firmware-5.7.html))。
- **5.8** (2026-07-21 発表): CTAP 2.3、`hmac-secret-mc` など。注目は **`previewSign`** で、WebAuthn L4 に提案中の署名の拡張。認証用とは別の資格情報で、加工しない任意の文を署名する。Yubico は用途に「人が承認する操作」「AI エージェントの操作の承認」を挙げている。ただし「試作」で「最終の仕様までに変わる見込み」とされ、関連する道具は「本番の暗号の指針に使わないこと」と明記されている ([5.8 の仕様](https://docs.yubico.com/hardware/yubikey/yk-tech-manual/yk5-firmware-5.8.html)、[発表](https://www.yubico.com/press-releases/yubico-extends-passkeys-beyond-trusted-authentication-to-verified-authorization-with-launch-of-yubikey-5-8/))。
- **YubiKey のファームウェアは更新できない** ([YSA-2024-03](https://www.yubico.com/support/security-advisories/ysa-2024-03/))。5.8 の機能を使うには新しい鍵が要る。本書の設計は 5.7 の機能だけで組み、5.8 の `previewSign` は仕様が固まってからの選択肢にとどめる。

### 2.3 EUCLEAK (YSA-2024-03、CVE-2024-45678)

- 対象: ファームウェア 5.7 未満の YubiKey 5 系列の **ECDSA**。FIDO は ECDSA を多く使う。PIV と OpenPGP は ECC の鍵を使うときだけ。
- 攻撃に要るもの: 鍵を物理的に手に入れること、専用の装置で演算を観測すること、対象のアカウントの知識。用途によっては PIN も。
- 推奨: 物理的に管理する、失くしたら登録を消す、PIV / OpenPGP の署名鍵は RSA か Ed25519 にする。ファームウェアの更新も交換の制度も無い。
- **手元の鍵は 5.7.4 と推定され、対象外**。それでも本書では FIDO2 と SSH は Ed25519 (`ed25519-sk`) を既定にする。予備の鍵を買うときは 5.7 以上を確かめる。

### 2.4 Windows の制約

- **FIDO2**: Windows 10 1903 以降、管理者でないアプリは FIDO の機器に直接 (HID で) 触れず、`webauthn.dll` を通す ([python-fido2 の WindowsClient の説明](https://developers.yubico.com/python-fido2/API_Documentation/autoapi/fido2/client/windows/index.html))。`webauthn.dll` を通すと Windows の「セキュリティ」の窓が出て、触れることが要る (一般知識、実測で確かめる)。触れずに使う設定 (`no-touch-required`) は Windows の経路では使えないという報告がある ([Win32-OpenSSH issue 2408](https://github.com/PowerShell/Win32-OpenSSH/issues/2408))。**所有者の確認に使う限り、これは利点である。**
- **PRF / hmac-secret**: `webauthn.h` では、旧来の hmac-secret の拡張は GetAssertion で「未対応」とされ、新しい版の GetAssertion の options に PRF の値を渡すと hmac-secret に変換される ([microsoft/webauthn](https://github.com/microsoft/webauthn))。libfido2 は Windows の経路で hmac-secret に対応し、1.17.0 (2026-04-15) で 64 バイトの salt にも対応した ([libfido2 NEWS](https://raw.githubusercontent.com/Yubico/libfido2/main/NEWS))。**手元の API は版 9 なので道はあるが、実際に取れるかは未確認。**
- **SSH**: Windows 付属の OpenSSH は 8.9 から FIDO 鍵に対応 ([Yubico の SSH の手引き](https://developers.yubico.com/SSH/Securing_SSH_with_FIDO2.html))。手元は `OpenSSH_9.5p2 for Windows`。ただし Win32-OpenSSH には sk 鍵の扱いの不具合の報告がある (鍵の生成で「機器を挿して」と出る [issue 2413](https://github.com/PowerShell/Win32-OpenSSH/issues/2413)、`no-touch-required` と `verify-required` を付けた鍵の署名が失敗する [discussion 2030](https://github.com/PowerShell/Win32-OpenSSH/discussions/2030))。`-Y sign` を sk 鍵で使えるかは調べた範囲で記述が無く、**Y0 の実測の最初の項目にする**。`ssh` と打つと Git の ssh が先に見つかることがあるので、`C:\Windows\System32\OpenSSH\ssh-keygen.exe` を明示する。
- **PIV**: Windows のスマートカードの仕組み (CCID) で、管理者なしに使える。手元でも `Microsoft Usbccid Smartcard Reader` として見えている。PIN の方針は生成時に決めて後で変えられない ([PIV の方針](https://docs.yubico.com/yesdk/users-manual/application-piv/pin-touch-policies.html))。
- **OTP**: 手元の鍵は USB の製品 ID が `0406` (FIDO+CCID) で、OTP の機能は USB で無効。チャレンジ応答を使うなら有効にする作業が要る。Windows では ykman の子プロセスが HID の排他で失敗するという報告もある (二次情報)。

### 2.5 Mathematica から使う道

Wolfram Language には FIDO やスマートカードを直接扱う関数が無い (一般知識、未確認)。外部のプログラムを呼ぶ。

| 道 | 追加のソフト | できること | 注意 |
|---|---|---|---|
| (a) `ssh-keygen -Y sign` / `-Y verify` | なし (Windows 付属) | 文への署名と検証。触れる・PIN は鍵を作るときの選択 | Windows での sk 鍵の `-Y sign` は要実測。検証時に UP / UV の印を確かめる方法も要確認 (4.1 節) |
| (b) 補助の exe (C# / .NET か Rust・Go) が `webauthn.dll` を呼ぶ | 自作 (小さい) | 署名と PRF。表示する RP の名前を決められる | 補助の exe の改ざんに備えてハッシュを固定する |
| (c) python-fido2 (`WindowsClient`) | pip で導入 | 同上。手元に Python 3.12 はあるが fido2 は未導入 | 導入は所有者の判断 |
| (d) PowerShell + .NET (CNG のスマートカード鍵) | なし | PIV の鍵で RSA-OAEP の復号・署名。PIN は Windows の窓 | ECC の鍵の扱いは要実測 |
| (e) age + age-plugin-yubikey | 導入が要る | PIV の鍵で包む。受取人を複数にできる | PIN の方針 once は実質毎回 PIN になる ([age-plugin-yubikey](https://docs.rs/age-plugin-yubikey/)) |
| (f) ykman | 導入が要る | 版の確認、PIV・OATH・OTP の設定 | 設定の道具。日常の処理には使わない |

どの道でも次を守る。秘密は引数に入れず標準入力で渡す。触れるのを待つ間に FE を止めない (`StartProcess` + tick で待つ。at-rest 方策 v0.2 の R 規則と同じ)。時間切れを決めて、失敗したら理由と次の手段を返す (文書 12 の C)。

### 2.6 先行事例

- **パスワード管理**: KeePassXC は HMAC-SHA1 のチャレンジ応答で保管庫の鍵を包み、FIDO2 hmac-secret の対応も議論している ([KeePassXC #9506](https://github.com/keepassxreboot/keepassxc/discussions/9506))。Bitwarden などは passkey の PRF で保管庫を解錠する ([Bitwarden の議論](https://community.bitwarden.com/t/encryption-prf-via-windows-hello-passkey/94236))。共通の形は**封筒暗号化** (データの鍵を、鍵ごとの KEK で包んで並べる) で、Yubico の手引きも同じ形を勧める ([PRF の開発者向け手引き](https://developers.yubico.com/WebAuthn/Concepts/PRF_Extension/Developers_Guide_to_PRF.html))。手引きの注意: PRF の出力をそのまま鍵にせず HKDF で用途ごとに導く、鍵を失えばデータを失う、ブラウザは salt を `SHA-256("WebAuthn PRF" || 0x00 || salt)` に変えるがネイティブの SDK は変えないので自分で用途を分ける ([hmac-secret の詳説](https://developers.yubico.com/WebAuthn/Concepts/PRF_Extension/CTAP2_HMAC_Secret_Deep_Dive.html))。
- **ディスク暗号化**: Linux の systemd-cryptenroll は FIDO2 hmac-secret か TPM2 + PIN で解錠し、回復鍵を別に持つ (一般知識、未確認)。
- **age-plugin-yubikey**: PIV の鍵で包む。触れる方針の既定は always。
- **SSH と git の署名**: `ed25519-sk` に `-O resident` (鍵に保存し、別の機で `ssh-keygen -K` で取り出せる)、`-O verify-required` (毎回 PIN)、`-O application=ssh:<名前>` (用途ごとに分ける) が推奨の形 ([Yubico の SSH の手引き](https://developers.yubico.com/SSH/Securing_SSH_with_FIDO2.html))。
- **YubiKey 5.8 の `previewSign`**: 「AI エージェントの操作の承認」を用途に挙げる。本書の方向と同じだが試作 (2.2 節)。
- **取引の確認**: WebAuthn の初版には認証器に文を表示させる拡張 (txAuthSimple) があったが、対応する機器が無く外された (一般知識、未確認)。**鍵に画面が無い問題は、業界でも解けていない**。表示は PC 側に頼る。

### 2.7 TOTP の位置づけ

- TOTP は、検証する側が同じ種を持つ。SourceVault で TOTP を検証するなら、種は SystemCredential に置くことになり、それを読めるコードは符号を作れる。**同じ PC の上で、所有者の確認として使っても守りは増えない。**
- YubiKey の OATH の利点は、使う側 (所有者のスマホや PC) から種を消せることにある。外部サービスの 2 要素としては有効。ただし FIDO2 に対応するサービスでは FIDO2 を優先する (フィッシングに強い)。
- SourceVault での使い道は、数字しか打てない遠隔の経路 (将来の Web 画面、スマホから LAN の SourceVault に方針の変更を送る場合など) の第 2 要素に限られる。効くのは攻撃者が遠隔にいる場合だけで、service 機の中に入られたら効かない。5C NFC ならスマホの Yubico Authenticator で符号を読める。本書では優先度を低くする。

## 3. 方針: 3 段のハイブリッド

### 3.1 段の定義

| 段 | 対象 | 鍵の在りか | 使うときの条件 | 理由 |
|---|---|---|---|---|
| **H0 日常・無人** | service の台帳の MAC 鍵 (ledger-mac・externalref・prompt・toolargs)、同期鍵 sync:v1、PL < 0.95 の作業データの at-rest 鍵、API キー、AutoTrigger の permit | SystemCredential (今のまま)。任意で TPM で包む (4.4 節) | なし | service は無人で動く。触れることを求めると止まる |
| **H1 所有者の判断** | 所有者 ticket の全 Action (AuthorizeInstruction・AcceptBaseline・ResolveFinding・Release・ChainRestart・遮断の解除・方針の緩和・WebGuard の許可ホスト・公開の fail-closed の解除など) | YubiKey の FIDO2 の資格情報 (SSH 形式の鍵)。検証は公開鍵 | 触れる (UP) | エージェントは触れられない。検証側に秘密が要らない |
| **H2 根** | 鍵束の書き出し・読み込み、鍵の交代と破棄、根の公開鍵 (H1・H2 の鍵) の登録・交代・失効、SecurityProfile を development にする、PL ≥ 0.95 の封印の解錠、予備の YubiKey の登録 | YubiKey の別の資格情報 (PIN 必須) と、封筒暗号化の KEK | 触れる + PIN (UV)。必要なら待ち時間と通知 | 1 回の操作が全体に効く |

### 3.2 YubiKey が手元に無いとき (ハイブリッドの規則)

文書 12 の原則 (止めずに受け入れ、記録して見直す) に合わせて、段ごとに扱いを変える。

- **H0**: 影響なし。
- **H1**: 移行期間は、今の HMAC の ticket (KeyId owner、ChoiceDialog) も受け付ける。ただし ticket に **確かさ** (Assurance) を記録し、YubiKey で後から**追認**するまで「仮」とする。仮の判断は SystemDoctor の View に並べ、追認しないまま期限を過ぎたものは Finding にする。Action ごとに必要な確かさの下限を表で持ち (`$SourceVaultOwnerTicketMinAssurance`、案)、仮を受け付けない Action (例: ChainRestart) も決められる。
- **H2**: YubiKey + PIN が必須。YubiKey を両方失ったときだけ、紙の回復用 passphrase で鍵束を開き、新しい YubiKey を登録する手順 (回復の手順) を使う。

確かさの値 (案):

| 値 | 意味 |
|---|---|
| `HardwareVerified` | YubiKey で触れて PIN も入れた (UP = 1, UV = 1) |
| `HardwarePresence` | YubiKey で触れた (UP = 1) |
| `PlatformPresence` | Windows Hello (TPM の鍵 + 顔か PIN) で確かめた (任意。3.3 節) |
| `SoftwareDialog` | 今の ChoiceDialog と HMAC |
| `Development` | development の鍵 (試験だけ) |

### 3.3 Windows Hello を間に入れる案 (任意)

Windows Hello も `webauthn.dll` の認証器で、鍵は TPM に置かれ、使うには顔か PIN が要る。YubiKey を持ち歩いて機の前に無いとき、H1 の代わりに `PlatformPresence` として使える。機ごとの鍵になる点は今の HMAC と同じだが、カーネルの中に秘密が無い点で HMAC より強い。Win32-OpenSSH で Windows Hello の鍵がうまく動かない報告 ([issue 2408](https://github.com/PowerShell/Win32-OpenSSH/issues/2408)) があるので、使うなら補助の exe の道 (2.5 節の b) で実測してから決める。

## 4. 設計案

### 4.1 所有者 ticket v2: 署名方式の追加

**形**: 今の ticket の欄 (Type・Version・Action・Principal・Subject・Bind・Nonce・KeyId・IssuedAtUTC・ExpiresAtUTC) はそのまま。KeyId に `owner-hw` (H1) と `root-hw` (H2) を足し、次の欄を加える。

- `Scheme`: `"sshsig-ed25519-sk"` (最初の版。補助の exe の道に変えるなら `"webauthn-es256"` などを足す)
- `SignerFingerprint`: 公開鍵の指紋 (SHA256)
- `Signature`: SSHSIG の文字列。署名する文は今の `iSVOTPayload` (`SourceVault_autotrigger.wl:820`) の正準の文字列をそのまま使い、namespace は `sourcevault-owner-ticket@v1`
- `AuthFlags`: 署名に入っている UP / UV の印、`Counter`: 署名の回数

**発行**: `SourceVaultOwnerTicketDialog` が今と同じく内容を見せ、所有者が承認したら、補助 (最初は `ssh-keygen -Y sign`) を `StartProcess` で起動する。Windows の窓が出て所有者が YubiKey に触れ、署名が返る。手元に置く鍵のファイル (`id_ed25519_sk…`) は YubiKey の中の資格情報への参照で、漏れても YubiKey が無ければ使えない。`-O resident` で作れば、2 台目の機で `ssh-keygen -K` で参照を取り出せる。

- H1 の鍵: `-O resident -O application=ssh:sourcevault-owner` (触れるだけ)
- H2 の鍵: `-O resident -O verify-required -O application=ssh:sourcevault-root` (触れる + PIN)

**検証**: 公開鍵だけで行う。
- 最初の版は `ssh-keygen -Y verify -f <allowed_signers> -I owner -n sourcevault-owner-ticket@v1 -s <署名>` を呼ぶ。
- 加えて SSHSIG の中身を Wolfram Language で読み、`AuthFlags` の UP = 1 を必須、H2 は UV = 1 も必須にする。`ssh-keygen` が検証の際に UP / UV を確かめるかは版で異なり、手引きにも曖昧さの指摘がある ([openssh-unix-dev 2025-01](https://lists.mindrot.org/pipermail/openssh-unix-dev/2025-January/041755.html)) ので、自分で読む。
- `Counter` が増えているかを鍵ごとに覚える (LocalState)。減ったら複製の疑いとして Finding にする。
- Wolfram Language の `VerifyDigitalSignature` で Ed25519 の署名を直接検証できるなら、外部の呼び出しを減らせる (要確認)。

**変わること**:
- service は秘密を持たずに H1 の ticket を検証できる (`$SourceVaultOwnerTicketKeyRef` が要らない Action が増える)。
- 2 台の機が同じ YubiKey の ticket を検証できる。ただし別の機で使い回されないよう、Subject に機の名 (`SourceVaultMachineTag[]`) を入れ、使用済みの記録は今と同じく機ごとにする。
- ticket を台帳に載せる処理 (Inc3 の `SourceVaultOwnerTicketCheckRecord`) は、署名方式に応じて検証を切り替える。

**公開鍵の固定 (§19.4)**: 公開鍵は秘密ではないが、差し替えられると攻撃になる。指紋を (1) SystemCredential、(2) 台帳の記録 (VerifierRegistration と同じ扱い)、(3) 紙、の 3 か所に置く。指紋の変更は、登録済みの H2 の鍵の署名 (相互署名) か、3.2 節の回復の手順でだけ受け付ける。

**共存**: `$iSVOTAcceptedKeyIds` (`SourceVault_autotrigger.wl:960`) に `owner-hw` / `root-hw` を足し、今の `owner` は確かさ `SoftwareDialog` として残す。

### 4.2 表示のすり替えへの対策

YubiKey には画面が無い。所有者が確かめられるのは PC の画面だけで、同じカーネルで動くコードが窓の中身を変え、別の ticket に触れさせることはできる (権限の取り違え)。触れさせる要求を何度も出して、所有者が疲れて触れるのを待つ手口 (いわゆる MFA 疲れ) もある。次で減らす。

1. **1 件ずつ**: 署名の要求が 1 つ保留されている間は、次の要求を受け付けない。
2. **別のプロセスでの照合**: 補助のプロセスが、署名する文から短い指紋 (例: 4 語か 6 文字) を計算して自分の窓に出す。FE の窓にも同じ指紋を出し、所有者が一致を目で確かめてから触れる。カーネルの中のコードは補助のプロセスの窓を書き換えられない (補助の exe の道で実現できる。ssh-keygen の道ではできない)。
3. **触れる回数を減らす**: 同時に起きた複数の判断を 1 回の署名にまとめる (Bind に複数の digest を入れる)。1 日の署名の回数を SystemDoctor の指標にし、多すぎたら知らせる。
4. **後から見直す**: YubiKey で署名した ticket はすべて台帳に載る。FE の View に「最近 YubiKey で承認したもの」を並べ、身に覚えの無いものを Finding にする (文書 12 の「所有者の判断も記録して見直す」)。
5. **運用の約束**: 自分で操作していないときに Windows の窓が出たら触れない。窓に出る RP の名前 (`ssh:sourcevault-owner` など) を確かめる。

### 4.3 鍵を包む (H2 と PL ≥ 0.95)

**形 (封筒暗号化)**: データの鍵 (今の `SymmetricKey`) を、KEK で包んで受取人の数だけ並べる。受取人は次の 3 つ。

- 主の YubiKey
- 予備の YubiKey (別の場所に保管)
- 紙の回復用 passphrase (今の scrypt の鍵束と同じ方式)

**KEK の候補**:

| 方式 | 良い点 | 弱い点 |
|---|---|---|
| (B) PIV の鍵 (X25519 で鍵共有、または RSA-OAEP)。age-plugin-yubikey か .NET の CNG | Windows で管理者なしに確実に動く。PIN と触れる方針を鍵ごとに固定できる。受取人を複数にする形が既にある | 署名用の FIDO2 とは別の機能を設定する。age-plugin-yubikey の PIN once は実質毎回 |
| (A) FIDO2 の PRF / hmac-secret | 署名と同じ機能で済む | Windows の経路での可否が未確認 (2.4 節) |
| (C) passphrase のみ (今) | 道具が要らない | カーネルに passphrase が入る |

**推奨**: まず (B) の PIV。(A) は Y0 の実測で取れることが分かってから選ぶ。

**解錠の時間**: H2 の解錠は FE のカーネルのメモリにだけ置き、期限を付ける (例: 30 分)。service には渡さない (詳しくは 8.1 節の「解錠の期間」、service への委任もそこで扱う)。ディスクの正本は常に暗号文にする (at-rest 方策 v0.2 の W2)。

**鍵束**: `SourceVaultExportKeyBundle` に YubiKey の受取人を足し、passphrase は紙の回復として残す。鍵束の書き出しそのものを H2 の操作にする。

**鍵の喪失への備え**:
- YubiKey は 2 本以上。両方を登録してから本番で使う。予備は 5.7 以上。
- FIDO2 の PIN は既定で 8 回続けて誤ると閉じ、戻すにはリセットしかない (資格情報がすべて消える)。PIV の PIN は 3 回で、PUK で戻せる (一般知識、未確認)。予備の鍵が回復の道になる。
- 紙の回復用 passphrase は金庫などに置き、年に 1 回、回復の訓練をする。

### 4.4 H0 (SystemCredential) の補強

H0 の鍵は今のまま SystemCredential に置く。そのうえで:

- **TPM で包む (任意)**: Windows の TPM の鍵 (取り出せない鍵) で SystemCredential の値を包むと、ディスクの複製や同期の誤りで値が持ち出されても、別の機では使えない。同じ利用者のプロセスは「使う」ことはできるので、動いている PC の中の攻撃には効かない。
- **使用量の記録**: `NB*WithKeyRef` の呼び出しを鍵ごとに数え、普段と違う量を SystemDoctor に出す。
- **はっきり書いておくこと**: H0 の鍵は、同じ利用者の権限で動くコードからは守れない。YubiKey で守れるのは H1 と H2 だけである。

### 4.5 SourceVault の外の入口

- **外部アカウント**: Dropbox・GitHub・Microsoft・Google に、主・予備の YubiKey をセキュリティキー (passkey) として登録する。TOTP より FIDO2 を優先し、SMS の 2 要素は外す。コードの変更は要らず、所有者の作業で効果が大きい。
- **GitHub**: push とコミット署名を `ed25519-sk` にすると、公開リポジトリへの書き込みに触れることが要る。「test codes/ を公開しない」「論文の本文を投稿前に公開しない」の最後の歯止めになる。ただし PackageAutoCommit の自動化とぶつかるので、自動化にはリポジトリを限った別の鍵 (H0) を残し、公開リポジトリへの push だけを H1 にする案を既定にする。
- **LAN の機**: LM Studio や llama.cpp の機に SSH で入るなら、その鍵も sk 鍵にする。

## 7. 守れないこと・残る危険

- **表示のすり替え**: 4.2 節で減らすが、なくならない。
- **解錠中のメモリ**: H2 で解錠した鍵、復号した平文は、期限まではカーネルのメモリにある。
- **H0 の鍵**: 同じ利用者のコードから守れない (4.4 節)。
- **所有者自身の誤り・物理的な強要**: YubiKey は「所有者が触れた」ことしか示さない。
- **紛失と PIN の漏れが重なること**: 失くしたら直ちに公開鍵の登録を失効させる (H2 の操作。予備の鍵で行う)。
- **形骸化**: 触れる回数が多いと、確かめずに触れるようになる。署名の回数を測り、まとめて署名できる形にする。
- **5.8 の `previewSign`**: 試作なので、本書では使わない。

## 8. 議論の記録 (2026-11-13): 解錠の期間と、PL の 3 段

所有者の問い: (1) PL ≥ 0.95 のデータを扱うワークフローで、秘匿データに出会うたびに YubiKey に触れて解除するのはきつい。一定期間有効なチケットを発行することになるという理解でよいか。(2) いま、みなしで PL 1.0 になっているファイルやノートブックのセルが多数ある。その大多数は、YubiKey による暗号化 (多要素認証) を要しない PL 0.9 程度のデータと思われ、PL を下げる設定の変更が要るのではないか。(3) 次の 3 段でよいか: 「暗号化 & 多要素認証が必須: PL ≥ 0.95」「暗号化 & SystemCredential で十分: オブジェクトストアの AccessLevel ≤ PL < 0.95」「秘匿が必要だが暗号化は不要: PL < オブジェクトストアの AccessLevel」。

以下は回答の案で、まだ決定ではない。

### 8.1 解錠の期間 (一定期間有効な解錠)

理解は正しい。ただし、所有者 ticket (1 回限り、特定の操作に束縛) とは別のものとして定義する。名前は「解錠の期間」(Unlock lease、案)。

- **開き方**: YubiKey に 1 回触れて PIN を入れる (H2 の操作、6.1 節の決定 2 で PIN は H2 だけ)。PIV で包んだ KEK をほどき、FE のカーネルのメモリにだけ期限まで置く。期間中は触れ直さない。
- **期間は SourceVault 側で持つ**: YubiKey の PIV にも「触れたことを覚える」方針 (cached) があるが 15 秒しか続かず (一般知識、未確認)、PIN の once はスマートカードの接続ごとなので、この用途には合わない。
- **期間に付ける制限 (案)**:
  - 主体: 所有者 (OwnerFE / OwnerCode) と、名前を挙げたワークフロー
  - データの種類: 例「成績だけ」(種類ごとに別の KEK にしておけば、種類ごとに開ける)
  - 期限: 時間の上限と、使わない時間の上限
  - 終わる条件: スリープ、画面のロック、FE の終了。取り消しのボタン
  - 機とカーネル: FE のカーネルだけ。service には渡さない (下の委任を除く)
- **無人のワークフロー (service)**: service は触れられない。2 つの道を用意する。
  - **委任**: 所有者が 1 回触れて「今日の 18 時まで、種類 X を service に預ける」と委ねる。範囲と期限は委任の記録に書き、台帳に残す。
  - **待ち行列**: 委任が無ければ、PL ≥ 0.95 を要する仕事は「解錠待ち」で待たせ、所有者に 1 回だけ知らせる。黙って失敗させない (文書 12 の C)。
- **受け入れる危険**: 期間中は、同じカーネルで動くコードも、範囲内の暗号を解ける。すべての復号を台帳に記録して後から見直せること、PL ≥ 0.95 の範囲を狭く保つことが前提になる。
- **復号とモデルへの提供は別の判定**: 期間中に復号できても、モデルに渡すかは今までどおり NBAccess と関所が判定する (クラウド LLM には 0.5 以上を渡さない、関所の段 2 など)。

### 8.2 みなし 1.0 の見直し

PL を下げる見直しは必要。順番が大事で、**PL ≥ 0.95 に YubiKey を必須にする前に分類を見直す**。出力の PL は入力の最大値を引き継ぐ (`SourceVaultEstimateOutputPrivacy` の MaxObservedInput) ので、みなしの 1.0 が残ったままだと、それに触れた派生物まで 0.95 以上になり、何をするにも触れることになる (形骸化)。

いま 1.0 になる主な出どころ (2026-11-13 にコードで確かめた):

| 出どころ | 場所 | 備考 |
|---|---|---|
| PL が付いていないときの安全側の既定 | ファイルの判定の既定 `NBAccess.wl:6608` / `:6622`、セルの PL の欠落 `NBAccess.wl:2985`、SourceVault の「PL 不明は 1.0」(`SourceVault.wl:4246`) | 送り先の判定の安全側として意図したもの |
| Eagle ライブラリの既定 | `$SourceVaultEaglePrivacyLevel = 1.0` (`SourceVault_eagle.wl:4063`) | at-rest 方策 v0.2 で 0.9 に変える予定だったが未実施 |
| ノート全体を Private にしたとき | `NBSetNotebookPrivate` で全セルが 1.0 (`NBAccess.wl:2176`) | 同じく 0.9 に変える予定だったが未実施 |

**提案**: 数値を 1 つずつ下げるのではなく、PL に **値の出どころ** を持たせる。

| 出どころ (案) | 意味 | 送り先の判定 | 保管の段 |
|---|---|---|---|
| `Declared` | 所有者が宣言した (セル・ノート・ファイル・種類の規則) | その値 | その値で決める (0.95 以上なら YubiKey) |
| `Default` | パッケージの既定 (Eagle の既定など) | その値 | 0.95 未満として扱う (SystemCredential の段) |
| `Unknown` | PL が付いていない (安全側の 1.0) | 1.0 のまま | SystemCredential の段として扱う |
| `Derived` | 入力から引き継いだ | 入力の最大値 | 入力の出どころを引き継ぐ (`Declared` の 0.95 以上から作った派生物は YubiKey の段) |

- YubiKey 必須の段は **`Declared` の 0.95 以上** (と、それから作った `Derived`) にだけ使う。新しく入ってくる不明なデータが YubiKey の段に積み上がらない。
- 派生物は値を引き継ぐ。成績の要約は成績として扱う。下げたいときは匿名化の手続き (declassify) を通す。
- 既に付いている値を一括で下げるのは方針の緩和になる。一覧 (場所・今の PL・出どころ・案の PL) で確かめてから所有者が決め、判断を記録する (文書 12 の E)。

### 8.3 PL の 3 段と保管先の AccessLevel

考え方は正しい。直す点と、表の案:

| 段 | 条件 (案) | 鍵 |
|---|---|---|
| 暗号化 & YubiKey 必須 | `Declared` (と `Derived`) の PL ≥ 0.95。保管先によらない | PIV で包んだ KEK (H2、解錠の期間) |
| 暗号化 & SystemCredential で十分 | 保管先の AccessLevel < PL < 0.95 (`Default`・`Unknown` の 1.0 もここ) | SystemCredential (H0) |
| 秘匿は要るが、その保管先では暗号化しない | PL ≤ 保管先の AccessLevel | なし。秘匿は送り先の判定で守る |

- **境界の向き**: NBAccess は「PL ≤ AccessLevel なら見せる」で作られている (`NBAccess.wl:5720`、送り先の `MaxAccessLevel >= accessLevel` も同じ向き)。これに合わせ、等しい場合は平文でよい側に入れた。0.95 ちょうどは at-rest 方策 v0.2 の DECISION-5 どおり暗号化する側。
- **保管先の AccessLevel は、見られる相手の最小**: Dropbox は Dropbox 社と同期しているすべての機器、Claude Code などが読む作業フォルダはクラウド LLM が読むので 0.45〜0.5 程度、GitHub の公開リポジトリは 0、同期しないローカルの場所 (LocalState など) はほぼ 1.0。
- **今の AccessLevel は送り先にしかない**: NBAccess の AccessLevel は送り先 (CloudLLM 0.5、LocalOnly / Notebook 1.0) のもので、保管先ごとの値 (v18 §10 の StorageProfile、`MaxPlaintextPL`) は未実装 (at-rest 方策 v0.2 §2.2)。この表は StorageProfile の実装を前提にする。
- **3 段目は「公開してよい」ではない**: その保管先の観測者には見えてよいというだけで、モデルや外部への送り出しは別の軸 (クラウド 0.5、プライベート LLM 0.8、関所の段) で守る。
- **0.95 の意味が変わる**: at-rest 方策 v0.2 では 0.95 は「Dropbox で平文にしてよい上限」(Dropbox の `MaxPlaintextPL` = 0.95) だった。本表では 0.95 は「YubiKey が要る境」になり、Dropbox には別に低い AccessLevel を決める。Dropbox の中で暗号化するデータが増える。
- **影響が最も大きい所**: MyPackages は Dropbox の中にあり、Claude Code の作業フォルダでもある。ここの AccessLevel は 0.45 程度になり、0.45 を超えるセルを含むノートブックはセル単位の暗号化 (at-rest 方策 v0.2 の §3.2・表示モード) が要る。

### 8.4 残る論点 (所有者の決定待ち)

1. Dropbox (エージェントが読まない場所) の AccessLevel をいくつにするか。v18 の案は 0.65、at-rest 方策 v0.2 は 0.95 (DECISION-1 の二段構成の一般側)。
2. 最上段 (YubiKey 必須) を、同期しないローカルの場所でも必須にするか (案は「保管先によらない」)。
3. `Unknown` を保管の上で SystemCredential の段として扱う案でよいか (at-rest 方策 v0.2 は「不明は 1.0 のまま、同期領域では暗号化しないと保存できない」としていた。案はこれを保ったうえで、鍵を H0 にするもの)。
4. 解錠の期間の既定の長さと、使わない時間の上限。service への委任を認めるか。
5. 値の出どころ (`Declared` / `Default` / `Unknown` / `Derived`) を入れるか、数値の見直しだけで済ませるか。

## 9. 運用の記録 (2026-11-13〜14)

### 9.1 外部アカウント (Y5)

- 2026-11-13: 所有者が Dropbox のパスキーを主の YubiKey に登録した。予備の鍵は届き次第、追加する。
- 確かめること: パスワードだけのサインインや SMS の 2 段階認証が残っていないか (最も弱い手段が全体の強さになる)、バックアップコードを紙に控えて PC の外に置いたか (予備が届くまでは唯一の回復の道)、ログイン中の機器の一覧に見覚えのないものが無いか。
- FIDO2 の PIN は、パスキーと、後で作る SSH 形式の鍵 (H1・H2) で共通。8 回続けて誤ると初期化しか戻す道が無く、登録したパスキーもすべて消える (一般知識、未確認)。

### 9.2 PIV の初期値の変更

2026-11-14、所有者が Yubico Authenticator の PIV の画面 (スロット 9a・9c・9d・9e はいずれも空、PIN・PUK・管理キーは既定値のまま) を見て、変えるべきかを尋ねた。回答:

- **変える**。決定 4 で鍵を包む方式に PIV を選んだので、いずれ使う。既定値は公開されており、そのままでは YubiKey を挿した PC で動くプログラムが、スロットに鍵を作る・書き換える・使うことができる。スロットが空の今が、何も失わずに変えられる時期。PIV は FIDO2 と別の機能で、変えても Dropbox のパスキーには影響しない。
- **PIN**: 6〜8 文字。FIDO2 の PIN とは別にする (片方を盗み見られても、もう片方は守れる)。
- **PUK**: 6〜8 文字。PIN と別にし、紙に控えて PC の外に置く。PIN と PUK はどちらも 3 回まで。PUK まで閉じると PIV の初期化しかなく、PIV の鍵がすべて消える (今は空なので失うものは無い)。
- **管理キー**: ランダムに生成し、画面にあれば「PIN で保護」を有効にする (管理キーを YubiKey の中に置き、PIN で使えるようにする。覚えなくてよい)。
- **順番**: PIN → PUK → 管理キー (PIN で保護するなら PIN を先に)。予備の鍵にも同じ作業をする。
- スロットの鍵の生成 (PIN の方針と触れる方針は生成時に固定) は Y4 で決める。今は作らない。

### 9.3 管理キーの方式 (TDES / AES-128 / AES-192 / AES-256)

- **AES-256 + PIN で保護** を勧める。AES-192 (5.7 の既定) でも安全上の差は無い。TDES は避ける。
- 管理キーを使うのは、スロットの鍵を作る・入れる・消すときだけで、日々の復号・署名は PIN で行う。どの AES でも総当たりの心配は無い。TDES は古い方式で、NIST でも新しい用途には使わない扱い。YubiKey は 5.4 から AES に対応し、5.7 で既定が AES-192 になった (既定の値そのものは変わっていない)。
- 管理キーは、後から値も方式も変えられ、変えてもスロットの鍵は消えない。PIN の方針・触れる方針とは違い、この選択は後戻りできる。
- **道具との相性**: TDES を前提にした古い道具がある。age-plugin-yubikey は少なくとも 0.5.0 の時点で「利用者が設定した、PIN で保護していない TDES 以外の管理キー」に対応しておらず、AES の管理キーへの対応は要望として残っている。他のライブラリ (Yubico.NET.SDK #160、piv-go #146) でも 5.7 の既定の変更で同種の不具合が出て直された。PIN で保護した AES の管理キーを最新の age-plugin-yubikey が扱えるかは未確認で、Y4 で道具を決めるときに確かめる。合わなければ、そのときに管理キーを変えればよい。

## 付録 A. Y0 の実測の手順 (案)

すべて本書を書いた機の付属 OpenSSH を明示して使い、cmd.exe で実行する (`%USERPROFILE%` と `<` は cmd.exe の書き方)。H1 の鍵の作成で YubiKey に資格情報が 1 つ増える (発見可能な資格情報 100 件のうち 1 件)。消すときは ykman か Windows の設定 (アカウント → サインイン オプション → セキュリティ キー) で行う。

1. 版と有効な機能の確認: `ykman info` (ykman の導入が要る)。導入しない場合は Yubico Authenticator の画面で確かめる。本書では USB の識別子 `VID_1050&PID_0406&REV_0574` から 5.7.4 (FIDO+CCID) と推定した。
2. H1 の鍵を作る (PIN を設定していなければ、先に設定を求められる):

```
C:\Windows\System32\OpenSSH\ssh-keygen.exe -t ed25519-sk -O resident -O application=ssh:sourcevault-owner -C sourcevault-owner -f %USERPROFILE%\.ssh\id_ed25519_sk_sourcevault_owner
```

3. 署名 (`t.txt` に適当な文を書いておく。`t.txt.sig` ができる):

```
C:\Windows\System32\OpenSSH\ssh-keygen.exe -Y sign -f %USERPROFILE%\.ssh\id_ed25519_sk_sourcevault_owner -n sourcevault-owner-ticket@v1 t.txt
```

4. 検証 (`allowed_signers` に `owner namespaces="sourcevault-owner-ticket@v1" ` + `.pub` の中身を 1 行で書く。cmd.exe で実行する):

```
C:\Windows\System32\OpenSSH\ssh-keygen.exe -Y verify -f allowed_signers -I owner -n sourcevault-owner-ticket@v1 -s t.txt.sig < t.txt
```

5. 確かめること: 触れずに待つと何秒で失敗し、どんな文が出るか。H2 の鍵 (`-O verify-required`) で PIN の窓が出るか。Mathematica から `StartProcess` で呼んで FE が止まらないか。2 台目の機で `ssh-keygen -K` で参照を取り出し、署名と検証ができるか。
