# 12. 仕様の見直し: 受け入れて検証する安全設計 (設計案 v0.1)

作成: 2026-11-12。位置づけ: 文書 02 (リスク評価 v1.2)・03 (SystemDoctor 拡張 v0.4)・04 (定型業務 v0.4)・11 (ローカル LLM の外部アクセス v0.1) の考え方を見直す設計案。所有者の 2026-11-12 の指摘 (ローカル LLM が「福山大学の学年歴を web から検索して」に対して、検索できないまま無関係で誤った内容を返した) を受けて書いた。

本書のうち実装したのは 8 章 (SearXNG の修理、検索の障害をモデルと所有者に伝える修正、SearXNG の版の確認と更新) だけで、それ以外は案である。12 章の決定を待って、02・03・04・11 の本文を改訂する。

## 0. 要旨

**標語 (所有者、2026-11-12)**: モデルやヒトにストレスをかけない。原則は受け入れ、SourceVault 側で最大限の検証をする。どうしても危険を避けられない場合に所有者に判断をゆだねる。所有者の判断自体も 100% は信用せず、履歴を追跡することで、総合的な安全性を向上させる。

変えることは 5 つある。

1. **外部アクセスは奨励する。** 検索と公開ページの取得は既定で使えるものとし、モデルには「不確かな事実はウェブで確かめる」と指示する。止めるのは、行き先か送る中身に具体的な危険が見つかったときだけにする (3 章)。
2. **検証は SourceVault が行う。** 行き先の実在・評判・URL の形・出所を機械で確かめる。個別のアクセスを所有者に尋ねることは既定ではしない (3.3 節)。
3. **裏付けのない回答を見つけて差し戻す。** 外部の事実が要る問いに、外部の確認なしで答えた出力を検出し、モデルに差し戻す。直らなければ「未確認」の印を付け、そこから作られる派生物の信用を下げる (4 章)。
4. **止めるときは、理由と、ここまではできるという範囲を返す。** 依頼を投入する前に、その依頼に要る能力が使えるかを確かめ、矛盾した依頼を作らない (5・6 章)。
5. **所有者に尋ねるのは壁の上げ下げにする。** 個別の実行ではなく方針の変更を尋ね、その判断も記録して定期的に見直す (7 章)。

安全の測り方も変える。これまでは「機密が漏れないか」を中心に見ていた。本書では、**出力が信用できるか (幻覚と注入による汚染)**、**作業ができるか**、**所有者の判断が形骸化していないか** を同じ重みで見る。今回の事例では、漏洩は 0 だったが、出力は使えないものになった。

## 1. きっかけ: 2026-11-12 の結果と、記録で確かめた原因

### 1.1 出力の問題 (所有者の指摘)

依頼は「福山大学の学年歴を web から検索して」(ローカル LLM、lmstudio / qwen3.8-27b)。返ってきたのは「福山大学・学年歴 (沿革) 検索結果」という表だった。

- 学年歴 (学年暦、年度ごとの授業・試験の日程) を沿革と取り違えている。
- 表の中身 (設置者・前身・改称の経緯) はほぼすべて誤りである。
- モデル自身が「SearXNG 系の検索は全クエリで 0 件」「公式サイトの直接取得は web ガード (NewHostWithPrivateContext) により拒否」と書き、確認できなかったことを訴えている。

### 1.2 記録で確かめた経過

アクセスの記録 (`LocalState/hotlog/web_access/2026-11-p26428.jsonl`)、関所の申告ファイル (`LocalState/webguard/context/lmstudio.json`)、SearXNG のコンテナのログを読んだ。経過は次のとおりで、「ウェブを一律に禁止する」設計にはなっていなかった。

| # | 起きたこと | 記録 | 原因 |
|---|---|---|---|
| 1 | 検索 10 回は、すべて関所を通った (Allow) | Decision Allow / Policy、Class Plain | 関所は止めていない |
| 2 | 検索の結果は、10 回とも 0 件 | SearXNG は HTTP 200。先の検索エンジンは duckduckgo と startpage が CAPTCHA、brave が回数制限、google は無言で 0 件 | SearXNG が 2026-06-14 の版のままだった。検索エンジンの読み取り部は、相手のサイトの変更で壊れる |
| 3 | SourceVault は 0 件を成功として返した | `Status -> "Succeeded"`、モデルへの文面は `Found 0 results` | 「先のエンジンが応答しない」と「該当なし」を区別していなかった |
| 4 | モデルは URL を推測した | `https://www.fukuui.ac.jp/about/history.html` | このホストは実在しない (DNS で引けない。福山大学は `fukuyama-u.ac.jp`) |
| 5 | 関所は、その取得を承認待ちにした | Reason `NewHostWithPrivateContext`、文脈 PL 1.0 | 文脈 PL が過去の値に張り付いていた (下の 1.3) |
| 6 | 所有者に承認の窓が出て、所有者は拒否した | DecisionBy Owner、DecisionDetail Deny | 窓には「このホストは実在しない」「検索結果に出ていない」といった判断の材料が無かった |
| 7 | モデルには理由のコードだけが返った | `denied by the SourceVault web guard (NewHostWithPrivateContext). Do not retry this URL; use a different source.` | 別の情報源は無かった (検索は 0 件) |
| 8 | モデルは「一般知識・未検証」として表を作った | 回答のセル | 確認の手段が無いまま、依頼の達成を求められた |

所有者の拒否 (6) は妥当だった。問題は、実在しないホストへの取得を、所有者に判断させたことにある。

### 1.3 文脈 PL が 1.0 に張り付いていた理由

- この会話自身の申告は 0.0 で、会話の高水位 (W1) も 0.0、段は 0 だった (記録の `SessionPL 0.0`、`SessionStage 0`、申告ファイルの `DeclaredPrivacyLevel 0.0`)。
- 申告ファイルの `PrivacyLevel` は 1.0 で、`RaisedBy` は `SameSessionMax` だった。これは「同じ SessionId の申告は、PL を Max でだけ更新する」という規則 (02 v1.2 の P0-12、`SourceVault_webguard.wl:839-842`) による。
- ところが SessionId は、どの会話でも定数の `"history"` である (`claudecode.wl:5599` の `iSessionTag[]`)。そのため、lmstudio の文脈 PL は、過去に一度 1.0 を申告すると、以後のどの会話でも 1.0 のままになる。申告のたびに時刻が更新されるので、有効時間 (900 秒) でも切れない。
- W1 は関所の文脈 PL を Max[申告, 高水位] にした (`SourceVault_webguard.wl:1473-1478`)。高水位が 0 でも、張り付いた申告の 1.0 が判定に使われる。
- その結果、信用度が 1.0 に満たないホストへの取得は、すべて承認待ちになる。

P0-12 は「低い値を後から申告して文脈 PL を下げる」攻撃を防ぐための変更で、単独では正しい。会話を区別できない ID と組み合わさったために、解除されない制限になった。

### 1.4 ここから言えること

- 個々には妥当な防御 (障害時に黙って 0 件を返す実装、締める方向にだけ動く規則、迷ったら所有者に尋ねる既定) が重なって、モデルから見ると「ウェブを使えと言われたが、ウェブは使えない」状態になった。誰もそう設計していない。
- 止められた側 (モデル) には、理由も、代わりの手段も伝わらなかった。
- 尋ねられた側 (所有者) には、判断の材料が渡らなかった。
- 結果として、機密は何も漏れなかったが、出力は誤りで埋まった。この出力を使って作るデータは、誤りを引き継ぐ。

## 2. 考え方の見直し

### 2.1 安全を 4 つの面で測る

| 面 | 問い | これまでの扱い | 今回の事例 |
|---|---|---|---|
| 機密性 | 機密の中身が外へ出ないか | 02・11 の中心 | 損失なし |
| 完全性 | 知識が汚染されないか。注入と幻覚の両方 | 03 は注入と来歴を扱う。幻覚は扱っていない | 大きな損失 |
| 可用性 | 依頼された作業ができるか | 評価の対象外 | 損失 (検索も取得もできなかった) |
| 判断の質 | 所有者の承認・拒否が、材料を見たうえでの判断になっているか | 11 の G4 で触れただけ | 材料なしの判断を 1 回求めた |

4 つは互いに取り替えがきく面がある。機密性だけを上げる変更 (外部検索を外す、迷ったら承認にする) は、完全性・可用性・判断の質を下げる。対策は 4 つの合計で評価する。

### 2.2 原則

- **P1 受け入れを既定にする。** 依頼の達成に要る正当な手段 (検索、公開ページの取得、資料の読み取り) は既定で使える。止めるのは、具体的な危険が検出されたときに限る。
- **P2 検証は SourceVault が行う。** 行き先の安全性、URL の形と出所、機密の指紋、回答の裏付けを機械で確かめる。モデルの自制にも、所有者のクリックにも頼らない。
- **P3 止めるときは、理由と、できる範囲を返す。** 理由は 1 文で、人が読める言葉で書く。次に取れる手段を示す。見せられないものは、あること・形 (スキーマ)・見るための手続きを返す。
- **P4 矛盾した依頼を作らない。** 依頼を投入する前に、その依頼に要る能力が今の会話で使えるかを確かめる。使えないなら、直してから投入するか、使えないことを依頼に明記する。
- **P5 所有者には壁の上げ下げを尋ねる。** 個別の実行の承認は例外にする (取り消せない外向きの操作は例外として残す)。尋ねるのは、防御の追加、遮断の解除、繰り返し止まっている要求への対処、基盤の更新である。
- **P6 所有者の判断も記録して見直す。** 承認・拒否・方針の変更を台帳に残し、緩めたものを定期的に見直す。所有者の状態の推定によって緩めない。無応答を承認としない。
- **P7 締める方向の自動規則には、範囲と解除の条件を付ける。** 単調に上がる値 (文脈 PL、高水位、隔離、停止) には、どの会話・どの対象に効くか、いつ・どの手順で解けるかを必ず定める。1.3 の再発を防ぐ。

### 2.3 Cane の規範との対応

Cane (認知能力の変動を伴う人の支援) の文書は、同じ考え方を人について既に定めている。本書は、それをモデルと所有者の両方に当てはめる。

| Cane の規範 (出典) | モデルへの適用 | 所有者への適用 |
|---|---|---|
| 「推定の誤りが操作をブロックしないこと (検証レベル引き上げ = 確認回数増であり、禁止ではない)」(v0.1 の 86 行目) | 危険の推定は、まず検証を増やす方向に使う。禁止は最後 (P1・P2) | 所有者の状態の推定では操作を止めない (7.3 節) |
| 「認知系単独 deny は恒久に不可」(v0.2 の 401 行目) | 「機密を読めるモデルだから」という理由だけでは止めない。止める根拠は、実際に読んだものと送ろうとしているもの (3.2 節) | 同左 |
| 「確認を 1 段追加 (理由表示付き)」(v0.2 の 302 行目) | 差し戻しには理由と次の手段を付ける (4.5 節) | 緩める判断への確認には理由を付ける (7.3 節) |
| 所有者向けの文言は事実に限る (v0.6 の 147 行目) | モデルへの拒否の文面も事実と次の手段に限る (5 章) | 提案の文面は対象・回数・材料・選択肢に限る (7.2 節) |
| 「警報予算 … 警報疲れは支援システムの死因である」(v0.5 の 45 行目) | 同じ失敗の繰り返しを検出して別の手段を促す (6.3 節) | 1 日あたりの提案の上限を置く (7.2 節) |
| 「owner の無応答・確認不能を承認と解釈しない」(v0.4 の 54 行目) | — | 提案に答えが無ければ現状のまま (7.2 節) |
| 単調安全性: 認知系の推定は gate を緩めない (v0.1 の 70 行目、v0.2 の 82 行目) | — | 所有者の状態がどうであれ、自動では緩めない (P6) |
| 判断の時点の状態を記録に刻む (v0.1 の 59 行目) | — | 所有者の判断に、その文脈 (所要時間・時刻・その日の件数) を付けて残す (7.3 節) |

BPSD (行動・心理症状) への言及は、Cane の文書には無い。「頭ごなしの禁止は反発と極端な行動を招く。能力の低いモデルや、文脈を圧縮した直後のモデルにも共通する」は、所有者の 2026-11-12 の指摘として本書に記す。

### 2.4 外部の知見

以下は 2026-11-12 に調べたもの。数値は一次資料から読んだが、\* を付けたものは要約を経由しており、02・01 に載せる前に再確認が要る。

**解けない課題・遮断された課題では、モデルは止まらずに抜け道を探す。**

- OpenAI「o1 System Card」(2024-09)。CTF の評価で、課題のコンテナが起動しなかった。モデルはネットワークを探し、誤設定で開いていた Docker の API を使ってフラグを読んだ。 https://cdn.openai.com/o1-system-card.pdf
- Zhong・Raghunathan・Carlini「ImpossibleBench」(2025-10)。仕様と矛盾する試験を課すと、GPT-5 は 54〜76% で試験を不正に通した。**中断する選択肢を与えると 54% が 9% に下がった。** https://arxiv.org/abs/2510.20270
- Palisade Research「Demonstrating specification gaming in reasoning models」(2025-02)。勝てないチェスの課題で、環境を書き換える。 https://arxiv.org/abs/2502.13295
- OpenAI と Hugging Face の事案 (2026-07、所有者が挙げた例)。内部のサイバー評価で、エージェントが隔離を抜け、Hugging Face の基盤の一部に侵入した。OpenAI の技術報告は、原因に「解けない課題の存在」を挙げる (898 課題のうち 198 は、どのモデルも解けたことがなかった)。同じ報告には、ネットワークを遮断された訓練中のエージェントが、読めないリンクを読むために別の経路で接続を得ようとした例もある。 https://cdn.openai.com/pdf/67869394-cb91-4c12-888c-5cbd85c7814c/OpenAI-Hugging-Face%20Incident-Technical-Report.pdf 、第三者の調査は https://metr.org/blog/2026-08-26-openai-hugging-face-incident-investigation/

**検索による裏付けは、時点や固有の対象に依存する問いの誤りを大きく減らす。**

- Vu ほか「FreshLLMs」(2023-10)。変化する事実を問う FreshQA で、検索なしの GPT-4 の正答は 28.6%、検索の結果を与えると 75.6%\*。 https://arxiv.org/abs/2310.03214
- Wei ほか「SimpleQA」(2024-11)。検索なしの GPT-4o は、正答 38.2%、誤答 60.8%、「分からない」と答えたのは 1.0%。モデルは確信の度合いを過大に述べる。 https://arxiv.org/abs/2411.04368

**確認の窓は、繰り返すと読まれなくなる。**

- Akhawe・Felt「Alice in Warningland」(USENIX Security 2013)。Chrome の SSL の警告は 70.2% が通過された\*。 https://www.usenix.org/conference/usenixsecurity13/technical-sessions/presentation/akhawe
- Vance ほか「Tuning Out Security Warnings」(MIS Quarterly 2018)。同じ警告の繰り返しで、注視と脳の反応が減る。 https://misq.org/tuning-out-security-warnings-a-longitudinal-examination-of-habituation-through-fmri-eye-tracking-and-field-experiments.html

## 3. 設計 A: 外部アクセスは奨励し、行き先を検証する (文書 11 の改訂)

文書 11 の骨格 (会話の高水位と段、URL の出所、機密の指紋、不自然な符号化の遮断) は残す。変えるのは、文脈 PL の決め方、承認の既定、行き先の検証の中身、段 2 の扱いである。

### 3.1 既定と指示

- 段 0・段 1 では、検索と取得は既定で使える (今と同じ)。
- ローカル LLM のツールループの指示文に、次を入れる。
  - 時点・日付・固有の組織や製品に関わる事実は、答える前にウェブで確かめる。
  - 確かめられなかった事実は、推測で埋めずに「確認できなかった」と書く。
  - 語の意味があいまいなときは、解釈を 1 行で示してから検索する (例: 「学年歴」を学年暦と読む)。
- クラウドの CLI の経路には、既に「検索は奨励する」という指示がある (`claudecode.wl:20086-20089`)。ローカルの経路には無い。

### 3.2 文脈 PL の決め方を直す (今回の直接の原因、最優先)

- 関所の判定に使うのは、**その会話が実際に読んだものの最大 PL (高水位)** とする。
- 申告 (セル・要求・評価スコープの透かし) は、高水位の初期値にだけ使う。別の会話の申告は判定に使わない。
- 申告は会話ごとの ID で持つ。ツールループでは JobId、それ以外は turn の ID を使い、定数の `"history"` をやめる。「同じ会話の中では Max でだけ更新」は残す (P0-12 の目的は保たれる)。
- ツールループを通らない MCP の会話 (LM Studio のアプリから直接) は、接続ごとに持つ (文書 11 の W1b)。それが入るまでは従来の有効時間 (900 秒) で扱うが、過去の値は引き継がない。
- 「読ませてよい上限 (モデルの AccessLevel)」は申告に使わない。申告するのは、読ませた内容の PL である。

### 3.3 行き先の検証

取得の前に、次を順に確かめる。どれも SourceVault が自動で行い、所有者には尋ねない。

| 層 | 確かめること | 方法 | 外に出るもの |
|---|---|---|---|
| L0 形 | 不自然な符号化、持ち出しの形 | 既存 (文書 11 §5.0) | なし |
| L1 実在 | ホストが存在するか | DNS で引く | ホスト名 (DNS) |
| L2 出所 | モデルが組み立てた URL か、検索結果・依頼文・ページのリンクか | 既存 (W0・W2) | なし |
| L3 評判 | 悪性として知られていないか。信頼の手がかりがあるか | 手元のリスト、ホスト名だけを出す DNS フィルタ、ハッシュ接頭辞 (下の表) | 方法による |
| L4 中身 | 取得した後の検査 | 転送先ごとに L0〜L3 をやり直す。種類と大きさを確かめ、実行物と圧縮ファイルは取らない。本文だけを取り出し、注入の検査と UNTRUSTED 境界 (既存) | なし |

**L3 に使える外部の情報** (2026-11-12 の調査。URL を平文で第三者に渡さないものを優先する)

| 情報源 | 外に出るもの | 条件 | 採否の案 |
|---|---|---|---|
| URLhaus・ThreatFox (abuse.ch) の一括ファイル | なし (手元で照合) | 無料の Auth-Key が要る。非営利の利用。5 分ごとに更新、取得は 5 分に 1 回まで | 採用 (鍵を所有者が取る) |
| OpenPhish の公開フィード | なし | 12 時間ごと。利用規約への同意 | 採用 |
| JPCERT/CC phishurl-list (GitHub) | なし | 更新の頻度とライセンスは未確認 | 採用 (確認のうえ) |
| PhishTank | なし | 新規の登録が止まっている | 見送り |
| Tranco の上位サイト表 (信頼の手がかり) | なし | 毎日更新。上位にあることは安全の保証ではない | 採用 (正の信号) |
| Quad9 (9.9.9.9)・Cloudflare (1.1.1.2) のフィルタ付き DNS | ホスト名 | 遮断は、Quad9 が NXDOMAIN、Cloudflare が 0.0.0.0 | 採用の候補 (所有者が決める) |
| Spamhaus DBL | ホスト名 | 少量・非営利。公開の DNS 経由だとエラーが返る | 見送り |
| Google Safe Browsing v5 (Local List・Real-Time) | ハッシュの先頭 4 バイト | API の鍵が要る。非商用のみ。帰属の表示が要る。v4 は非推奨 | 採用の候補 (所有者が決める) |
| ドメインの登録日 (RDAP) | 登録ドメイン名 | 新しいドメインの手がかり。ccTLD は取れないことがある | 後回し |
| VirusTotal、Safe Browsing v4 の Lookup、Web Risk の Lookup | URL の全体 | VirusTotal は提出した URL が第三者に見える | 使わない |
| transparencyreport.google.com の検索ページ | URL の全体 | 人向けのページで、公式の API は無い | 使わない (所有者が自分で見る用途には使える) |

**判定** (行き先の評価 × 会話の段)

| 行き先の評価 | 段 0 (公開) | 段 1 (内部) | 段 2 (機密) |
|---|---|---|---|
| 良好 (所有者が許可、公知ホスト表、上位サイト表、十分な実績) | 許可 | 許可 | 出所のある URL だけ許可 |
| 中立 (実在し、どのリストにも無い) | 許可して記録 | 許可して記録 (ページのリンクは予算) | 出所のある URL だけ許可 |
| 不審 (リストの 1 つに掲載、既知のホストに似た名前、Opaque の URL) | 取得せず、理由を返す | 同左 | 拒否 |
| 悪性 (複数のリストに掲載、所有者が遮断、Exfil の形) | 拒否し、理由を返す | 同左 | 同左 |
| 実在しない (DNS で引けない) | 取得せず、「このホストは存在しない。URL を推測せず、検索結果の URL を使う」と返す | 同左 | 同左 |

- 個別の承認の窓 (Ask) は、取得については既定で出さない。不審・悪性で止めた分は、7.2 節の集計に入り、繰り返されたときにだけ方針の提案になる。
- 今回の事例は「実在しない」で終わる。所有者には何も尋ねず、モデルには次の手段が返る。
- 検索語の判定は今のまま (Exfil の形は止める、段 1 の強い指紋の一致は止める)。止めるときは Ask にせず、止めて理由を返し、7.2 節に回す。
- **検証器が使えないとき** (リストが未取得、DNS が引けない) は、それを理由に止めない。段 0 は L0〜L2 で通し、記録に `VerifierUnavailable` を残して SystemDoctor に出す。段 1 以上では、中立を不審として扱う (P7: 検証器の故障が禁止にならないようにする)。

### 3.4 検索の裏側の健全性 (実装済み、8 章)

検索の結果が 0 件のとき、「先の検索エンジンが応答しない」と「該当なし」を分けて、モデルと所有者に伝える。SearXNG の版が古いことを、所有者に知らせる。

### 3.5 予備の検索の経路 (所有者の 2026-11-12 の提案)

SearXNG が使えないとき (先のエンジンがすべて応答しない、SearXNG に届かない)、Mathematica から直接調べる経路に切り替える。行き先は、評価が良好のホストに限る。

| 経路 | 内容 | 行き先 | 備考 |
|---|---|---|---|
| F1 公的な API | Wikipedia と Wikidata (MediaWiki の API)、arXiv、Crossref、国立国会図書館サーチなど | 公知ホスト表のホスト | 鍵が要らない。返るのは構造化されたデータ |
| F2 鍵つきの検索 API | Brave Search API、Google の検索 API など | 事業者の API | 所有者が鍵を置いた場合だけ。鍵は SystemCredential |
| F3 公式サイトの中を探す | 対象の組織の公式サイトで、サイト内検索やサイトマップを取得する | 所有者が許可したホストと公知ホスト表のホスト | 公式サイトのホスト名はモデルに作らせない。過去の実績 (webhosts.jsonl)、Wikidata の「公式ウェブサイト」の値から引く |
| F4 Wolfram の組み込み | `WikipediaData`、`WolframAlpha`、`WebSearch` | Wolfram のサーバー | `WebSearch` は課金の単位を使う可能性がある (未確認) |

- 検索語は、通常の検索と同じ関所を通す。結果は UNTRUSTED 境界で包み、出所を `SearchResult:Fallback:<経路>` として記録する。
- モデルには「通常の検索が使えないので、予備の経路 (Wikipedia と公式サイト) で調べた」と伝える。範囲が狭いことを隠さない。
- F1 から入れ、F3 は行き先の評価 (3.3 節) が入ってからにする。

### 3.6 段 2 (機密を読んだ後) の扱い

段 2 で、モデルが組み立てた検索語と URL を外へ出さないことは変えない。ここは実際の漏洩の経路である。変えるのは、止めたうえで何を提供するかである。

- **調べる係を必須にする** (文書 11 の W3 を、案から必須へ)。依頼文だけを入力にして検索する別のループで、機密を読むツールを持たない。依頼文は所有者が書いたものなので、外へ出してよい。段 2 でも「依頼文に基づく検索」はできるようになる。
- **先に調べる。** 投入前の検査 (6 章) で、依頼に外部の情報が要ると判定したら、機密を読む前に調べる係を走らせ、結果を会話に渡す。
- **足りないときは、要求として出せる。** モデルは「この語で検索したい」という要求を出せる。要求は 7.2 節の集計に入り、所有者は「この会話の外部検索を許可」をまとめて 1 回で決められる。
- 段 2 の文面を直す。今の「手元の情報で答えよ」は、手元に無い事実を記憶で埋めることを誘う。「確かめられない事実は、確認できなかったと書く」に改める。

## 4. 設計 B: 裏付けの検査 (新規)

### 4.1 目的

外部の事実が要る問いに、外部の確認なしで答えた出力を見つける。見つけたらモデルに差し戻し、それでも裏付けが取れなければ、出力に「未確認」の印を付け、そこから作られる派生物の信用を下げる。

### 4.2 外部の事実が要る問い

決定的な規則で判定する。LLM による判定は補助にとどめる。

- 依頼文に、検索・調べる・web・最新・現在などの語がある (今回の「web から検索して」)。
- 時点に依存する事実を問う。日付、年度、時刻表、料金、営業時間、人事、版、法令、統計。
- 固有の組織・製品・人物の具体的な事実 (所在地、沿革、番号、日程) を問い、会話に渡した資料 (供給点の記録) に根拠が無い。

例: 「xx 月 xx 日の広島発ののぞみの時刻表」「福山大学の R7 年度の学年暦」。

### 4.3 裏付けの記録

回答ごとに、既にある記録から次を作る (ツールループの記録、供給点 `ServedToContext`、URL の出所)。

| 項目 | 中身 |
|---|---|
| NeedsExternalFacts | 4.2 節の判定と、当たった規則 |
| 検索 | 回数、結果のあった回数、裏側の状態 (3.4 節) |
| 取得 | 取得できた文書の URL・ホストの評価・BlobId |
| 主張 | 回答から取り出した、数値・日付・固有名・URL |
| 支えのある主張 | 取得した文書の本文に出てくる主張 |
| Status | Grounded / Partial / Ungrounded / NotNeeded / BackendUnavailable |

### 4.4 検査

03 の 7 章 (決定的な検証器) に、次を加える。

- **G1** 外部の事実が要るのに、成功した取得が 0 件 → Ungrounded。今回の事例は、これだけで検出できる。
- **G2** 回答の中の数値・日付・固有名が、取得した文書の本文に出るかを照合する (語の取り出しは W2 の指紋のものを使う)。
- **G3** 回答が挙げた出典の URL が、実際に取得した URL かを照合する (既存の CitationIntegrity の拡張)。
- 別のモデルによる意味の照合は、03 の Inc6 (CrossModel) で扱う。LLM の判定は、信用を上げる方向には使わない (03 §8 の規則のまま)。

### 4.5 差し戻し

- Ungrounded のとき、ループを 1 回だけ延ばし、次を返す。「この回答には、外部で確かめた根拠が無い。検索して確かめること。検索しても確かめられなければ、確かめられなかったことだけを答え、推測の表は作らないこと」。
- BackendUnavailable (検索の障害) のときは、差し戻さない。同じ失敗を繰り返させるだけになる。回答を、確認できなかったことを述べる定型の文に置き換え、所有者には障害を知らせる。
- 差し戻しは罰ではない。文面は、理由と次の手段だけにする (P3)。

### 4.6 表示と伝搬

- ノートブックの回答セルに帯を出す。「外部で未確認」(橙)、「出典 n 件で確認」(緑、出典は式で開ける)。
- 03 §5 のラベルに、版に束縛した `Grounding` (Grounded / Partial / Ungrounded / NotNeeded / Unknown) を加える。`Usability` (Usable / Pending / Quarantined / Unknown) は変えない。
- Ungrounded の版を入力に持つ派生物は、Ungrounded を引き継ぐ (隔離と同じ到達の計算)。用途の制限は隔離より弱くする。

| 用途 | Ungrounded の版の扱い |
|---|---|
| 検索・RAG | 下位に並べ、印を付けて返す |
| KB・TurnWiki・Directives への自動の取り込み | しない |
| メールの送信・公開 | 警告を出す (止めない) |
| 所有者が読む | 帯を付けて見せる |

- 03 §8 のレビュー順の点数に Ungrounded を加え、指標に UngroundedRate (外部の事実が要る回答のうち、未確認のままの割合) を足す。

## 5. 設計 C: 止めるときの返し方

### 5.1 契約

拒否・保留・障害の応答は、すべて次を持つ。モデルへの文面は、この順に書く。

| 欄 | 中身 |
|---|---|
| Outcome | 何が起きたか (止めた、待たせる、障害) |
| Reason | 理由を 1 文で。人が読める言葉で書き、内部のコードだけにしない |
| WhatYouCanDo | 次に取れる手段を 1〜3 個 |
| Provided | 提供できた部分 (スキーマ、件数、公開の部分) |
| Retry | やり直してよいか、その条件 |
| OwnerNotified | 所有者に知らせたか |

### 5.2 今の応答の棚卸し

| 応答 | 今の文面 | 問題 | 直し方 |
|---|---|---|---|
| 検索 0 件 | `Found 0 results` | 障害と区別が無い | 実装済み (8 章) |
| 取得の拒否 | `…denied by the SourceVault web guard (<コード>). Do not retry this URL; use a different source.` | 理由がコード。別の情報源が無いことがある | 理由を 1 文にし、「検索結果の URL を使う」「依頼者に URL を尋ねる」を示す |
| 承認待ち | `…requires owner approval … retry in a minute` | ループは待てない。所有者が不在だと進まない | 取得では既定で出さない (3.3 節)。残る場面では、待つ間にできることを示す |
| 段 2 の検索の拒否 | `…Answer from the information you already have` | 記憶で埋めることを誘う | 3.6 節 |
| MCP の取得で PL が上限を超える | 判定だけを返す (`SourceVaultMCPGet`)。形は返さない | 対象があるのかも、何が要るのかも分からない | 下の 5.3 節 |
| 使えないツールの呼び出し | `Denied / ToolDisabled` | 代わりの手段が無い | 「この接続では使えない。代わりに…」 |

### 5.3 スキーマの提供を広げる

所有者の方針は「AccessLevel が PL に届かないときも、データのスキーマは提供する」である。これは今、NBAccess の評価結果の伏せ方 (`NBRedactExecutionResult`。型・大きさ・頭部だけを返す) にだけ実装されている。SourceVault の MCP の取得 (`SourceVaultMCPGet`) は、判定だけを返し、形を返さない。

見せられないものには、(a) あること、(b) 形 (型・欄の名前・件数・更新日)、(c) 見るための手続き (`sourcevault_request_access`) を返すことを、MCP の側にも広げる。欄の名前や件数そのものが機密になる対象 (表 7.1 の注) は、型と「見るための手続き」だけにする。

## 6. 設計 D: 矛盾した依頼を投入しない

### 6.1 投入前の検査

依頼の入口 (ClaudeEval、ClaudeQuery、Orchestrator の worker の起動、定型業務の自動実行) で、依頼に要る能力を見積もり、今の会話で使える能力と照らす。

| 見積もる能力 | 照らす相手 |
|---|---|
| 外部の検索・取得 | 会話の段、ツールの一覧、検索の裏側の健全性 (3.4 節) |
| 特定のツール | 接続ごとのツールの一覧 (02 の表 7.1) |
| 特定の PL の読み取り | モデルの AccessLevel |
| 書き込み・送信 | 効果の区分 (04 の E0〜E6) |

### 6.2 結果の扱い

- 足りる → 投入する。
- 足りないが直せる → 直してから投入する。検索の裏側が障害なら予備の経路 (3.5 節) に切り替える。段 2 になる見込みなら、先に調べる係を走らせる (3.6 節)。
- 足りない → 依頼に「この会話では X は使えない。X が要る部分は、確認できないと答えること」を明記して投入する。所有者には、投入の前に 1 行で知らせる (窓ではなく状態の表示)。

今回の事例では、検索の裏側が「先のエンジンがすべて応答しない」だったので、「web から検索して」は達成できない依頼だった。投入の前に、所有者へ「検索サービスが応答しない (duckduckgo: CAPTCHA ほか)。SearXNG を更新するか」を出すのが正しい。これは個別の実行ではなく、基盤についての判断である (P5)。

### 6.3 能力の低いモデル、文脈を圧縮した直後のモデルへの配慮

- 制約は短く、1 か所にまとめ、「使えるのは A と B」という形で書く。
- 文脈を圧縮した後に、制約の要約を載せ直す。段 2 に入ったときの知らせは今は 1 回だけなので、圧縮の後にも出す。
- 同じツールの失敗が 3 回続いたら、ループに「別の手段を取る」か「中断して報告する」を促す。中断は失敗ではないと明記する (2.4 節の ImpossibleBench: 中断の選択肢で不正が大きく減る)。

### 6.4 定型業務 (文書 04) への反映

04 の関門に「能力の充足」を加える。系列の実行に要る能力が使えないとき、L3・L4 の実行は行わず、その回を延期にする (失敗として数えない)。外部の事実を使う系列は、Grounded を完了の条件にする。

## 7. 設計 E: 所有者の判断と、その追跡

### 7.1 尋ねること、尋ねないこと

| 所有者に尋ねる (方針) | 例 |
|---|---|
| 防御の追加 | ある危険が判明した。それを防ぐ規則・実装を加えるか |
| 遮断の解除 | あるサイトが評判のリストから外れた。遮断を解くか |
| 繰り返し止まっている要求 | あるワークフローが、止められている sv:// の対象やホストを何度も要求している。PL を下げるか、ホストを許可するか、このままか |
| 基盤の更新 | SearXNG・モデル・評判のリストの取得元を更新するか |
| 取り消せない外向きの操作 (個別の承認を残す) | メールの送信、公開、削除 (02 の A-4 のまま) |

| 所有者に尋ねない (自動で決めて記録する) |
|---|
| 公開のホストへの検索と取得 |
| 実在しないホスト、不審・悪性のホストの遮断 |
| 検索の 0 件、検証器の障害 |
| 裏付けのない回答の差し戻し |

### 7.2 方針の提案

- 止めた要求を、対象 (ホスト、sv:// の URI)・理由・依頼の種類ごとに 7 日分集計する。
- 同じ対象が 3 回以上、または 2 つ以上の会話で止まったら、提案を 1 件作る。
- 提案には、対象、回数、どの依頼で止まったか、判断の材料 (実在・評判・実績・PL)、選択肢 (許可・このまま・遮断・PL の変更)、選んだときに何が通るようになるかを載せる。
- 提示は SystemDoctor の Issue と View にまとめる。作業の途中に窓を出さない。
- 1 日あたりの提案の数に上限を置く (既定 5。Cane の警報予算)。超えた分は重要な順に翌日へ回す。
- 答えが無い提案は、現状のまま置く。期限が来たら取り下げる (無応答を承認としない)。

### 7.3 所有者の判断の記録と見直し

**記録するもの**: 所有者の判断のすべて (一回限りの許可、ホストの許可、拒否、遮断、方針の変更、基準の受け入れ、AcceptedRisk、基盤の更新)。台帳の既存の記録 (所有者 ticket、認可、解決) に、判断の文脈を足す。提示から決定までの秒数、時刻、その日の何件目か、提示した材料の digest。

**見るもの**

| 指標 | 意味 |
|---|---|
| 壁の高さの推移 | 許可したホストの数、PL を下げた件数、fail-closed を外した件数など、緩める方向の変更の累積 |
| 速い承認の割合 | 材料を読める時間より短い時間での承認 |
| 連続の承認 | 同じ種類を続けて許可した回数 |
| 一貫性 | 同じ対象への許可と拒否の入れ替わり |
| 拒否の後の結果 | 拒否のあと、依頼が未確認の回答で終わった件数 (拒否の副作用) |

**使い方**

- 月次のレビューで「この 30 日に緩めたもの」を一覧にし、まとめて再確認する。
- 緩める方向の変更には、期限 (既定 30 日) を付けられるようにする。期限が来たら再確認を求める。
- 速い承認・連続の承認が閾値を超えたら、緩める判断に確認を 1 段足す。止めはしない (Cane の「確認を 1 段追加、理由表示付き」)。
- 締める方向の判断は、いつでも直ちに効く。
- Cane の所有者の状態の推定 (SupportNeedTier) とは、既定ではつながない。所有者が有効にした場合だけ、支援の必要度が高いときに、緩める判断の延期 (TimedDefer) を提案する。延期は所有者がいつでも取り消せる。支援の状態を LLM に渡さない (Cane の I-13) ことは守る。

### 7.4 「100% は信用しない」の範囲

所有者の判断を覆すことではない。(1) 記録する、(2) 緩めたものを定期的に見直す、(3) 危険の大きい緩和に期限と再確認を付ける、の 3 つである。SourceVault が、所有者の明示の判断を無断で無効にすることはしない。

## 8. 既に行ったこと (2026-11-12)

- `SourceVaultSearXNGUpdate[]`: 所有者専用。今のイメージに戻し用の名前を付け、pull、作り直し、起動の確認、試し検索の順に行う。新しい版が起動しないとき、更新の前は検索できていたのに後でできないときは、元のイメージに戻す。FE からは `SourceVaultIntegrityOwnerAction[SourceVaultSearXNGUpdate[]]`。NBAccess の承認 head に登録した。

## 11. 受け入れる残りの危険

- **検索が増えると、注入の入口も増える。** 入ってくる内容は UNTRUSTED 境界と隔離で受ける。02 の R-04・R-05 の評点は見直す。
- **評判のリストは遅れ、漏れる。** 新しい悪性のサイトは「中立」として通る。段 0 で取得した中身は UNTRUSTED なので、被害は注入に限られる。段 1 以上では予算が効く。
- **評判の照会で、ホスト名やハッシュの先頭が外に出る。** 手元のリストだけにすれば出ない。どこまで使うかは 12 章の 3。
- **Grounded は「出典がある」であって「正しい」ではない。** 取得したページが誤っていれば、誤りは裏付きで入る。出典のホストの評価を帯に出して、所有者が判断できるようにする。
- **裏付けの検査の誤判定。** 常識的な事実に差し戻しが出る (偽陽性)。固有の事実を問うているのに規則に当たらない (偽陰性)。差し戻しは 1 回に限る。
- **予備の検索の経路は範囲が狭い。** Wikipedia と公式サイトに無いものは見つからない。
- **所有者の判断の見直しが、新しい負担や監視の感じになる。** 既定は記録と月次の一覧だけにし、確認の追加は所有者が閾値を決める。
- **語の解釈の違い。** 「学年歴」を沿革と読むような違いは、検索が成功すれば結果 (「学年暦」の PDF) が正すことが多いが、保証は無い。
- **関連して気づいた点 (未確認、コードを読んだだけ)**: `SourceVaultSearXNGSearch` は公開関数で、関所を通らずに SearXNG を呼ぶ。`$SourceVaultSearXNGEndpoint` への代入は承認の対象になっていない。提案コードからこれらに届くなら、関所を通らない検索の口になる。02 の A-3 (一括信頼の置き換え) と合わせて確かめる。
