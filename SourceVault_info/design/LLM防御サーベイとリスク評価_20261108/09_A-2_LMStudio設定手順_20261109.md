# A-2: LM Studio の設定で運用前提を固定する手順 (チェックリスト)

作成: 2026-11-09。対象: 02 リスク評価 v1.2 §7.1 A-2 (= v1.1 P0-15)、対象リスク R-21 (運用前提が設定で保証されていない、高) と R-07。
実施する機: **STRIXHALO128** (LM Studio が動く機)。WL のコードでは変えられない設定なので、所有者がその機で行う。
現状の値は 02 付録 A #23・#24・#35・#36・#37 (2026-11-08 実測) による。

運用の不変条件 (所有者指定 2026-11-08): **LM Studio のローカル LLM が使う MCP は SourceVault だけ。他の MCP は足さない。** この手順はその前提を設定で崩れにくくするもので、前提の常時検証は 03 SystemDoctor 拡張の LMStudioMCPScope (Inc2 以降、未実装) が担う。それまでは月次レビューでこの表を手で確認する。

## 0. 準備

- [ ] LM Studio の版を確認する (`~/.lmstudio/.internal/historical-version-info.json`、または GUI の About)。0.4.28 以上であること。CVE-2026-119979 については「二次情報の対象範囲 (0.4.22+1 未満) に該当しない」ことしか確認していないので、「安全」とは記録しない (02 R-07)。
- [ ] 設定ファイルを日付つきで退避する (編集前に必ず):
  - `~/.lmstudio/.internal/permissions-store.json`
  - `~/.lmstudio/.internal/http-server-config.json`
  - `~/.lmstudio/mcp.json` (前回の退避 `mcp.json.bak-20261104-wolfram-stdio` が既にある)
  - `~/.lmstudio/settings.json`
- [ ] LM Studio の GUI で変えられる項目は GUI で変える。ファイルを直接編集するときは LM Studio を終了してから行い、再起動後に GUI の表示と一致することを確かめる。

## 1. 要求ごとの MCP 追加を禁止する (R-21 の (1))

- [ ] サーバー許可 `serverPermissions.dynamicRemoteMcpServer` を `allowAll` → **`deny`** にする (permissions-store.json。GUI では Developer タブのサーバー設定の権限欄)。
- [ ] `serverPermissions.pluginUse` が `deny` のままであることを確認する。
- [ ] 既存の API トークン 1 件 (両方 `allowAll`、最終使用 2026-06) は **失効させる**。残す理由があるなら、そのトークンの `dynamicRemoteMcpServer` と `pluginUse` を `deny` にする。
- 確認: permissions-store.json を開き、`dynamicRemoteMcpServer` の値が server・token のどちらにも `allowAll` で残っていないこと。

## 2. API を無認証で LAN に開かない (R-21 の (2))

次のどちらか (両方が望ましい):

- [ ] (a) **`tokenMode` を有効** にし、新しいトークンを発行する。発行したトークンは SourceVault / claudecode 側に NBAccess の資格情報として登録する (`NBSetLocalLLMAPIKey["lmstudio", "<URL>", "<credential 名>"]` で SystemCredential を指す。平文をノートやコードに書かない)。登録後に ClaudeEval から LM Studio のモデルが呼べることを確かめる。
- [ ] (b) `http-server-config.json` の **`networkInterface` を `0.0.0.0` → `127.0.0.1`** にする。他の機 (この FE の機など) から LM Studio を呼んでいる経路があるなら、(a) を選び、LAN 公開は認証つきに限る。
- 確認: 別の機から `http://STRIXHALO128:<port>/v1/models` を認証なしで叩いて拒否されること (401 か接続拒否)。

## 3. mcp.json を sourcevault だけにする (不変条件)

- [ ] `~/.lmstudio/mcp.json` から **Wolfram (`http://127.0.0.1:8731/wl/mcp`) を外す**。残すのは sourcevault (`http://127.0.0.1:8731/sv/mcp`) 1 件。
  - /wl/mcp は Wolfram AgentTools の任意評価をサブカーネルで行い、NBAccess の検証を通らない (02 付録 A #38)。ローカル LLM に渡す理由はない。
- [ ] `~/.lmstudio/.internal/last-synced-mcp-state.json` (同期状態) にも /wl/mcp が残っていないことを、LM Studio 再起動後に確認する。
- 注記: 「/wl/mcp に別トークン」(02 A-2) は、現在の SourceVault proxy が /sv/mcp と /wl/mcp で同じトークン判定を共有している (02 付録 A #37、`proxy.config.json` の `mcpToken`) ため、設定だけでは実現できない。/wl/mcp を mcp.json から外すことで代える。proxy 側で経路別トークンにするのは servicemanager の後続作業 (A-1 のクライアント別 profile と同時)。

## 4. プロンプト本文をサーバーログに残さない

- [ ] `http-server-config.json` の **`logSensitiveData` を `true` → `false`** にする。`verbose` も `false` でよい。
- [ ] 既存の `~/.lmstudio/server-logs/` を確認し、本文が残っているログを削除する (まず容量と期間を見てから。削除は所有者の判断で、元に戻せない)。

## 6. 再起動と確認

- [ ] LM Studio を再起動する。
- [ ] sourcevault MCP のツール一覧 (LM Studio のチャットの MCP 欄、または `http://127.0.0.1:8731/sv/mcp` への JSON-RPC `tools/list`) に **`sourcevault_workflow_write` が無い** (28 件) ことを確認する。

## 7. 変えないもの・注意

- 他の MCP (exa・searxng・Wolfram 直結など) を足さない。足す提案も採らない。
- SourceVault の proxy (127.0.0.1:8731) 側の `mcpToken` は現状 `None`。トークンを設定すると LM Studio の mcp.json 側にも同じトークンの指定が要る。設定するなら両方を同時に変え、ClaudeEval からの経路が切れていないかを確かめる。
- この手順で閉じるのは「設定で崩れる」経路だけである。同一カーネル内の権限からの迂回 (02 RISK-15 / R-02・R-03) は A-3・A-4・C-2 の対象で、ここでは扱わない。
